# 採用済み画像のGitHub配置ルール

更新日: 2026-09-17

## 目的
ChatGPTで生成・採用済みになった画像を、記事Previewブランチへ最短・安全に配置するための標準手順を定める。

## 原則
- 採用済み画像は再生成しない。
- `main` には記事画像を直接入れず、記事作業中は対象の `preview-*` / `ai-*` / `pilot-*` ブランチへ配置する。
- 画像差し替え後は、記事HTMLと画像資産だけが意図した差分になっているか確認する。
- Git Data APIで画像バイナリを安全かつ安定して直接登録できる場合は、直接配置を優先する。
- ただし、GitHub接続がローカルファイルを直接受け取れず、大容量Base64文字列をツール入力へ載せる必要がある場合は、Base64を無理に使用しない。通信エラー、切断、破損、サイズ不足が起きた経路を同じ形で繰り返さない。
- 画像バイナリのBase64文字列を会話本文、作業ログ、Markdown、JSON依頼ファイルへ大量出力しない。

## 採用確定後の扱い
- ユーザーが「採用」と明示した画像は固定扱いとし、明示的な再生成指示がない限り作り直さない。
- Hero / OGP / 本文図の採用対象を取り違えない。
- 同じ記事で複数候補を生成した場合は、最後に採用された画像だけを配置する。
- 採用済み画像の見た目を、配置時の都合でトリミング・合成・文字追加・再生成しない。
- Web最適化は、縦横比や内容を変えない範囲の形式変換・圧縮に限定する。
- Hero / OGP は原則として採用時の元解像度を維持し、容量削減だけを目的とした縮小は行わない。
- WebP化は可。ただし目視で劣化が分かる強圧縮は禁止し、迷う場合は軽量化より画質を優先する。
- 形式変換後は、掲載対象ファイルのバイト数とSHA-256を記録する。

## Hero / OGP の表示ルール（見切れ防止）
- 採用画像は「画像全体を見せる」ことを標準とし、表示枠に合わせるための勝手なズーム・トリミングをしない。
- HeroをCSS背景として使う場合、採用画像全体を見せる必要がある画像に `background-size: cover` を使わない。`cover` は枠の縦横比によって上下左右を切り落とすため、明示的にトリミングを許可された場合だけ使用する。
- Hero背景は原則 `background-size: contain`（複数背景の場合は画像レイヤーだけ `contain`）とし、`background-repeat: no-repeat` で全体を表示する。
- `background-position` だけで構図を無理に寄せない。PC / タブレット / スマホで主要人物・文字・小物が見切れていないことをPreviewで確認する。
- 画像の余白が発生する場合は、画像を拡大して切るのではなく、Hero側の背景色・グラデーション・レイアウトで自然に埋める。
- `<img>` でHeroやカード画像を表示する場合も、全体表示が要件なら `object-fit: contain` を使用し、`object-fit: cover` はトリミング許可時のみ使用する。
- OGP画像ファイルは原則として採用画像そのものを保持し、HTML/CSS側で切り抜いた画像をOGP用ファイルとして扱わない。
- OGPの `og:image` / `twitter:image` は、SNSクローラーがJavaScriptを実行しない前提で、最終公開ページの `<head>` に静的metaとして記述する。JavaScriptによる後付けだけに依存しない。
- OGP画像の縦横比が各SNSの表示枠と異なる場合、サービス側で中央クロップされる可能性がある。重要な文字・ロゴ・人物は端へ寄せすぎず、採用前またはPreview確認時にセーフエリアを確認する。
- ただしSNS側のクロップ対策を理由に、採用済み画像を無断で再トリミング・再生成しない。必要な場合はユーザー確認を取る。

## 標準ルートA: Git Data API直接配置
GitHub接続が画像バイナリを安定して直接扱える場合の第一選択とする。

1. 採用済み画像を会話内または作業コンテナから取得する。
2. 必要ならWeb用に最適化し、元解像度・画質を維持する。
3. 掲載対象ファイルのバイト数とSHA-256を計算する。
4. 画像バイナリをGitHub blobへ登録する。
5. 対象Previewブランチの現在HEADとtreeを確認する。
6. 画像blobを目的のパスへ追加した新treeを作る。
7. 必要なら同じcommitでHTMLの画像参照も更新する。
8. 現在のPreviewブランチHEADをparentにしてcommitを作る。
9. `update_ref` で対象Previewブランチをfast-forwardする。
10. GitHub側のファイルサイズ・blob・Preview表示を確認する。

### 直接配置を中止する条件
- `create_blob` 等の入力が文字列/Base64しか受け取れず、ローカルファイル参照を直接渡せない。
- Base64化後の巨大なツール入力で通信エラーや切断が発生した。
- 保存後のファイルサイズが元ファイルと一致しない。
- デコード・画像署名・SHA-256等で同一性を保証できない。

上記のいずれかに該当する場合、同じBase64転送を繰り返さず、標準ルートBへ切り替える。

## 標準ルートB: 検証付きバイナリ転送（Base64回避）
2026-09-17に実機検証したフォールバック経路。対象は**公開サイトへ掲載予定の非機密画像**に限定する。

使用する恒久Workflow:
- `.github/workflows/binary-image-transfer.yml`

一時依頼ファイル:
- `.github/binary-transfer-request.json`

### 手順
1. 採用済み原本を保全し、必要ならWebP等へ変換する。変換後の掲載対象ファイルについて、バイト数とSHA-256を計算する。
2. 公開予定の非機密画像だけを、Firestorage等の承認済み一時保管先へ**最短の保存期間**で一時配置する。原則1時間程度を優先し、長時間保管を常態化しない。
3. 対象 `preview-*` / `ai-*` / `pilot-*` ブランチへ `.github/binary-transfer-request.json` を作成する。画像本体やBase64は入れず、次のメタデータだけを記録する。
   - `share_id`
   - `file_id`
   - `file_name`
   - `sha256`
   - `size_bytes`
   - `target_path`
4. Workflowは一時保管先のメタデータから、指定したfile ID・file name・byte sizeが一致することを確認する。
5. WorkflowはHTTPSでバイナリを直接取得する。Firestorage経路では、短期download URLのホストを `s3.ap-northeast-1.wasabisys.com` に限定する。
6. 取得後、次をすべて検証する。
   - 最大5 MiB以内
   - 指定したbyte sizeとの完全一致
   - SHA-256完全一致
   - WebP / PNG / JPEGの実ファイル署名と拡張子の一致
   - `target_path` が `assets/images/` 配下
   - 実行ブランチが `preview-*` / `ai-*` / `pilot-*` であり、`main` ではない
7. 検証済みバイナリを一時領域に保持したまま、GitHubブランチの最新HEADを再取得する。
8. 依頼JSONのSHA-256が処理開始時から変わっていないことを確認する。依頼が変更・削除されていれば古い処理を中止する。
9. 最新HEAD上へ検証済み画像を置き、画像のSHA-256を再確認してからcommitする。同時に依頼JSONを削除する。
10. push競合が起きた場合は最新HEADを再取得して最大3回まで安全に再試行する。`force` pushは使わない。
11. GitHub上で保存後のbyte sizeを確認し、可能ならGit blob SHAも元ファイルから計算した値と照合する。
12. 一時保管期限を待たず削除できる仕組みがある場合は、GitHub保存確認後に削除する。

### Git blob SHAの照合
GitHub上のblob SHAは、通常のファイルSHA-256とは別物である。ローカルファイルから次で照合できる。

`SHA-1("blob <byte-size>\0" + raw-bytes)`

GitHubのcontents APIが返す `sha` と一致すれば、Gitへ保存されたバイト列が同一であることを追加確認できる。

## 並行作業・競合への対応
- Workflow処理中に別作業が同じPreviewブランチを更新しても、古いHEADをそのままpushしない。
- commit直前に最新HEADへ同期し、依頼JSONが処理開始時と同一であることをSHA-256で確認する。
- 依頼内容が変わった場合は、自動的に古い転送を中止する。
- pushが非fast-forwardで弾かれた場合は、最新HEADへ同期して安全に再試行する。
- 競合回避のために `force` pushを使用しない。

## セキュリティ境界
- 標準ルートBは、最終的に公開するWebサイト画像だけに使用する。
- パスワード、顧客データ、設備の機密資料、非公開写真、秘密鍵、認証情報、内部限定文書などを公開共有型の一時保管先へ送らない。
- 機密・非公開ファイルでは、private storage / private broker等の承認済み非公開転送経路を使用する。適切なprivate経路がなければ転送を停止する。
- 一時保管先の共有URLをGitHubの公開ログ、記事HTML、PR本文へ記録しない。
- SHA-256は機密値ではないが、原本の同一性確認用途として扱う。

## Previewブランチの鮮度と本番反映
- 作業中に `main` が進んだ場合は、Previewブランチが `behind` になっていないか必ず確認する。
- Previewブランチが古い `main` から分岐していても、確認済みPreviewをそのまま雑に `main` へ丸ごとマージしない。
- 本番反映時は最新 `main` を基準にし、ユーザーが承認した記事差分と採用画像だけを取り込む。
- 関係ない並行作業、古い一時コミット、別記事の差分を本番へ持ち込まない。
- `force` を使ったref更新は原則禁止。
- 本番反映直前にも `main...preview-*` または最終取り込み対象の差分を確認する。

## 使用するGitHub操作の基準
直接配置ルートでは、利用可能な場合は次を使う。
- `create_blob`
- `create_tree`
- `create_commit`
- `update_ref`

テキストファイルだけを追加・更新する場合は `create_file` / `update_file` を使ってよい。

Base64回避ルートでは、毎回新しい転送Workflowを作らない。恒久Workflow `.github/workflows/binary-image-transfer.yml` と一時依頼JSONだけを使用する。

## 禁止する転送方法
- 大容量Base64文字列を会話へ表示して人手で転記する。
- 通信エラーや破損が出た巨大Base64経路を、そのまま何度も繰り返す。
- 記事ごと・画像ごとに一時的なGitHub Actions workflowを新設する。
- 共有ページをPuppeteer等で開いて画像をスクレイピングする。
- 画像取得のためだけに `main` へ一時画像や一時依頼ファイルを置く。
- `force` pushで並行作業を上書きする。
- SHA-256・byte size・画像署名を確認せずに外部一時保管先から取得した画像を採用する。

## 2026-09-17 実証記録
Base64を使わず、1,167,170 bytesのlossless WebPで次を確認した。

- 元ファイル SHA-256: `d4a609346181ff3e8c8a757de20b10ce4142b19a80d637c6bc7bcf4fecd8640c`
- GitHub保存後サイズ: `1,167,170 bytes`
- Git blob SHA: `78d45cb3da2d0e12abd05e7550cf6195d7e6ccaf`
- 元ファイルから計算したGit blob SHAとGitHub contents APIの `sha` が一致した。
- 恒久Workflow + 小型JSON依頼方式で、Base64なしのバイナリ転送に成功した。
- 意図的に別commitを転送中の同一ブランチへ追加した競合試験でも、そのcommitを保持したまま最新HEADへ追従し、検証済み画像のcommitに成功した。
- 直接バイナリ転送の初期試験では1,167,170 bytesの原本に対して6,936 bytesしか保存されない失敗を検出したため、その経路は採用しなかった。

この検証により、GitHub接続がローカル画像を直接安全に受け取れず、大容量Base64が不安定な場合の標準フォールバックとして、検証付きバイナリ転送ルートを採用する。

## 最終確認
- 採用画像そのものを使っている
- 再生成していない
- 掲載用ファイルのSHA-256とbyte sizeを記録した
- GitHub保存後のbyte sizeを確認した
- HeroとOGPの参照先が正しい
- Hero / OGP が不必要にズーム・トリミングされていない
- PC / タブレット / スマホで主要要素が見切れていない
- OGP metaが最終公開ページのheadに静的に存在する
- 既存本文画像を消していない
- 英語版を触っていない
- affiliate URLを触っていない
- 記事承認前にmainへ記事画像を入れていない
- 一時依頼JSONが転送完了後に残っていない
- 記事専用の一時転送Workflowが残っていない
- Preview URLで最終確認できる状態になっている
