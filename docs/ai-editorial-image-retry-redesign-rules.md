# Denkicontrol AI編集部 画像再生成・再設計ルール v1.1

## 1. 目的
この文書は `docs/ai-editorial-article-image-strict-rules.md` を補強し、本文図解・hero・OGPが品質ゲートを通過しない場合に、同じプロンプトの再試行だけを繰り返して案件をERRORへ落とさないための必須ルールを定める。

本ルールは新規記事・記事更新のAI生成画像に適用する。

## 2. 基本原則
- 画像品質ゲートの不合格は「API失敗」と「設計失敗」を分けて扱う。
- 画像APIが正常応答したのに品質不足の場合、それは生成エラーではなく `QUALITY_REDESIGN` と扱う。
- 1成果物 = 1案件キューを維持し、不合格画像のために新しい案件や重複PRを作らない。
- 同じ command_id、同じ記事ブランチ、同じPRで修正を続ける。
- 同一プロンプトを機械的に3回繰り返して終了してはならない。

## 3. 画像生成前の「図解設計書」を必須化
本文図解は、画像生成APIへ渡す前に1枚ごとの図解設計書を作る。

各画像で最低限、次を記録する。
- `image_role`: overview / comparison / mechanism / process / check-flow / troubleshooting / technical
- `section_id`: 挿入対象の本文節
- `learning_goal`: この画像だけで読者に何を理解させるか
- `main_message`: 1文で表した主メッセージ
- `layout`: 2カラム比較、横方向フロー、中央主図＋周辺注釈、上下段など
- `required_visuals`: センサ、モータ、矢印、光軸、ワーク等、必ず描く視覚要素
- `required_labels`: 必ず読める必要がある短い日本語ラベル
- `verified_facts`: 公式資料で確認済みの事実だけ
- `prohibited_claims`: 推測してはいけない仕様・配線・数値
- `character_usage`: none / guide-only / active
- `mobile_priority`: スマホ縮小でも残すべき要素
- `gold_reference`: どのスター・デルタ採用画像の構成品質を主に参考にするか

この設計書がない本文図解は生成開始しない。

## 4. 生成プロンプトの必須構造
画像生成プロンプトは最低限、次の順番で組み立てる。

1. 画像の教育目的
2. 読者レベル beginner / intermediate / advanced
3. レイアウト指定
4. 必須の視覚要素
5. 必須ラベル
6. 公式確認済み事実
7. 禁止事項
8. スター・デルタ採用画像相当の情報階層・視線誘導・図解密度
9. キャラクター使用条件
10. スマホ可読性条件

「高品質」「分かりやすく」「おしゃれに」だけの抽象指示は禁止する。

## 5. 再生成は毎回原因別に変更する
品質不合格になった場合、IMAGE REVIEWERの指摘を次の原因カテゴリに分類する。

- `TEXT`: 日本語文字崩れ、長文、小さすぎる文字
- `FACT`: 技術的誤り、未確認仕様、構造の誤り
- `LAYOUT`: 構図、視線誘導、情報階層が弱い
- `DENSITY`: 情報不足または詰め込みすぎ
- `ROLE`: 比較図なのに違いが視覚化されていない等、用途不一致
- `CHARACTER`: キャラクターが主役になり技術内容を邪魔している、または不一致
- `MOBILE`: 縮小時に主要情報が消える
- `BRAND`: Denkicontrol / ゴールドスタンダードとの統一感不足

再生成時は、該当カテゴリに応じて設計書または構図を変更する。同じプロンプトの末尾に「前回指摘を直す」と追記するだけは禁止する。

## 6. 3段階リトライ
### Attempt 1: 初回生成
図解設計書に従って生成する。

### Attempt 2: 局所修正
初回レビューで落ちた原因だけを具体的に直す。
例:
- 文字量を半分にする
- 2カラムへ変更する
- 主図を中央へ集約する
- キャラクターを補助役へ下げる
- 矢印・番号を追加する

### Attempt 3: 全体再設計
2回目も不合格なら、同じ構図を維持してはいけない。
- storyboard / layout を作り直す
- 情報量を再配分する
- 必要なら1枚を2枚に分割する
- 逆に重複情報が多い場合は統合する
- ゴールドスタンダードの別画像を参考構造へ切り替える

## 7. 3回不合格時の扱い
3回不合格でも、画像API自体が正常なら案件を即 `ERROR` / `FAILED` にしない。

次の順に処理する。
1. `QUALITY_REDESIGN` へ遷移
2. 失敗した画像だけを再設計
3. 記事全体の本文図解構成を再確認
4. 必要なら画像枚数・役割・section割当を変更
5. 同じcommand_id / branch / PRで生成工程を再開

案件を `ERROR` にしてよいのは、認証・API障害・保存失敗・GitHub書込み失敗など、処理継続不能なシステムエラーの場合を原則とする。

品質不足はシステムエラーではない。

## 8. 技術文字の扱い
画像生成モデルに正確な日本語・数値・端子記号・細かな仕様表を過度に任せない。

- 画像内文字は短い見出し・大きなラベルを中心にする。
- 正確な数値表、型式仕様、長い説明はHTML本文へ残す。
- 日本語文字崩れが2回続く場合は、画像内の文言をさらに短くする。
- それでも正確な文字情報が不可欠な場合は、AI生成した主図・イラストを使い、文字だけを決定論的に後段組版するハイブリッド方式を許可する。
- ハイブリッド方式でも、AI生成した主図を単純なSVG箱図へ置換してはならない。

## 9. レベル別再設計
### beginner
- キャラクター、アイコン、吹き出しを積極的に使ってよい。
- ただし画像の主役は「理解させたい技術内容」とする。
- 文字より図・矢印・比較・順序で理解させる。

### intermediate
- キャラクターは多用してよいが、実務判断・選定・切り分けが主役。
- 比較条件、判断分岐、原因→確認の関係を図で見せる。

### advanced
- 再設計時も「かわいくして通す」方向へ逃げない。
- キャラクターは最小限。
- 回路・信号・タイミング・構造・因果関係・条件差を主役にする。
- 技術的正確性と可読性を最優先する。

## 10. ログ要件
不合格画像ごとに次を内部記録する。
- image index / slug
- attempt番号
- reviewer score
- failure categories
- reviewer issues
- 次回変更する設計項目
- 採用/不採用

管理画面へは同じ文章を何度も流さず、要点だけを表示する。
例:
`本文図解3/5: 88点。文字量と構図を再設計して再生成します。`

## 11. Preview完成条件への追加
次を満たさない限り `NEEDS_HUMAN` にしない。
- 全本文図解が採用済み
- 不合格画像がHTMLに残っていない
- 3回不合格後に設計変更なしで強制採用していない
- ゴールドスタンダード比較を通過
- Preview組込み後に画像サイズ・文字・スマホ表示を確認

## 12. 禁止事項
- 同一プロンプトを3回繰り返して案件をERRORにする
- 品質不足をシステム障害として扱う
- 失敗した本文画像のために新規案件・新規PRを作る
- scoreだけを見て原因分析をしない
- 3回目も1回目と同じ構図を使う
- 文字崩れを放置したまま採用する
- スター・デルタ画像より明らかに説明力が低い画像を「95点だから」で採用する
- 品質ゲートを下げて通す

## 13. 実装上の必須状態
Article Builderは少なくとも次の状態を区別する。
- `body_generate`
- `body_review`
- `body_retry`
- `quality_redesign`
- `body_done`
- `system_error`

`quality_redesign` は失敗ではなく、同じ案件内の正常な再設計工程として扱う。

## 14. OGPはhero・本文図解と別の品質ゲートで審査する
OGPは本文教材図やheroの縮小版ではない。役割は、SNS、検索周辺、一覧、共有カードで見た人の視線を止めて記事へ誘導する「看板」である。

### OGPの役割
- `ogp_role = attention-first-character-brand`
- 最優先は、縮小された状態でも「なんだこの電気サイト？」と一瞬で目が止まること。
- Denkicontrolの先輩・後輩キャラクターをブランドフックとして積極的に使う。
- 記事テーマの主役機器・現象を大きく1つ見せる。
- 技術内容を理解させる本文図解と同じ情報量を詰め込まない。

### OGPの推奨構成
1. 先輩・後輩キャラクターを主役級に配置
2. 記事テーマの主役機器または現象を大きく配置
3. 短く大きい日本語タイトルまたは問い
4. 必要なら1つだけ補助メッセージ
5. 太い輪郭・高コントラスト・十分な余白

小さな説明文、細かい凡例、長い仕様列挙、細線だけで成立する図は禁止する。

### OGPでのキャラクター品質
- キャラクターを使う場合は `assets/images/character-templates/senpai-kouhai-character-template.png` を正本とする。
- キャラクター同一性は数値スコアとは別の必須条件とする。
- 顔、髪型、服装、ヘルメット、年齢感、全体シルエットが正本から大きくずれた場合は `CHARACTER_FATAL` として不合格。
- 生成APIが画像参照入力に対応している場合、テキストだけで「同じキャラ」と指示する方法を合格経路にしてはいけない。
- 正本テンプレートを参照できない生成経路では、キャラクター同一性の合格判定を出さない。

### OGPの技術品質
- OGPはインパクトを優先してよいが、技術的な誤認は許可しない。
- 安全機器でないものを安全機器に見せる、存在しない配線や端子を描く、機器の向き・位置関係を逆にする等は `FACT_FATAL` とする。
- `FACT_FATAL` または `CHARACTER_FATAL` が1件でもあれば、総合点が95点以上でも不合格。

### OGPの採点軸
OGPは本文図解とは別に次を審査する。
- `attention_impact`: 一覧・SNSで視線を止める力
- `thumbnail_readability`: 小さくしても主題が残るか
- `character_brand_match`: 正本キャラとの一致
- `topic_recognition`: 記事テーマが一瞬で分かるか
- `technical_correctness`: 誤認・誤配置がないか
- `site_identity`: Denkicontrolらしさ

総合95点以上に加え、`FACT_FATAL=0`、`CHARACTER_FATAL=0` を必須とする。

### OGP再設計
3回不合格時はERRORにせず `QUALITY_REDESIGN OGP` へ移行する。
- Round 1: 情報を減らし、主役機器・短いタイトル・キャラクターを大きくする。
- Round 2: 前案を捨て、完全に別構図へ変更する。キャラクターを主役級にし、主題を1メッセージへ絞る。
- どちらも同じcommand_id / branch / PRを維持する。
- Round 2まで失敗した場合のみ、品質未達として人間確認または明示的な停止へ移す。システム障害としてのERROR表示とは区別する。

## 15. hero / OGP / 本文図解の役割分離
- `hero`: 記事を開いた後の入口。技術的に正確で、記事テーマと主役機器が一瞬で理解できることを優先。キャラクターのインパクトは必須ではない。
- `OGP`: 記事を開く前の看板。キャラクターと強い主題で視線を止める。ただし技術的誤認は禁止。
- `本文図解`: 読む負担を減らし、比較・原理・手順・切り分けを理解させる教材。キャラクターは理解補助として使う。

3種類を同一の評価プロンプト・同一の構図思想で作ってはならない。
