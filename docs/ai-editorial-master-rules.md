# Denkicontrol AI編集部 マスタールール v1.3

## 1. 位置づけ
この文書は、DenkicontrolのAI編集部が記事・画像・Preview・公開判断を扱う際の実行上の正本とする。

既存文書と矛盾した場合の優先順位は次の通り。
1. `docs/ai-governance.md` の安全・法令・人間の権限・秘密情報保護などのPrinciples
2. 本文書 `docs/ai-editorial-master-rules.md`
3. `docs/ai-editorial-article-image-strict-rules.md`
4. `docs/article-workflow.md`
5. `docs/new-article-checklist.md`
6. `docs/image-generation-rules.md` / `docs/article-type-templates.md` / `docs/reference-notes/**` / `docs/terminology/**`
7. `docs/agents/**` の個別Agent手順

下位文書が上位文書と矛盾した場合は上位を優先し、矛盾を発見したAgentは記録・修正候補として報告する。

## 2. 役割の正本
### ChatGPT / AI編集部
- 記事テーマ・重複・検索意図・既存記事を確認する。
- メーカー公式一次情報を中心に技術調査する。
- 完成済み記事HTMLから最適なコピー元を選定し、完成HTMLを作成する。
- 記事画像を生成する。
- 監査・反証・修正を実行する。
- 日本語記事Step 1では、記事HTML・画像を完成させ、AIがGitHubの確認用ブランチ等へ反映できる運用を標準とする。

### Codex
- 記事本文をゼロから執筆する主担当にしない。
- 配置、静的チェック、リンク・ファイル存在確認、限定的な細修正、Step 2導線整備等を担当する。
- 個別依頼では許可ファイルを最小化し、`docs/agent-runbook.md` に従う。

### 管理者
- Previewで記事全体を目視確認する。
- MEDIUM/HIGHの本番公開を最終判断する。
- NGの場合は「画像イメージが違う」「文章が多く見にくい」等の目的・問題点だけを指示してよい。具体的な修正方法はAI編集部が設計する。

## 3. 記事案件の標準フロー
1. 管理者指示
2. GitHub main・ルール最新版確認
3. 既存記事・検索意図・重複・カニバリゼーション確認
4. 公式一次情報調査
5. EDITOR設計
6. CHALLENGER反証
7. 必要な再設計
8. 標準コピー元 `articles/short-ground-leakage-basic.html` を取得し、完全コピーから制作開始
9. 記事HTML完成
10. TECHNICAL / SEO監査
11. 必要画像の用途判定・設計・生成
12. 画像自己評価 + ゴールドスタンダード比較 + 独立IMAGE REVIEWER
13. HTMLへ採用画像を組み込み
14. コピー元差分・HTML内部・リンク・画像・PC/スマホ等の自動検査
15. GPTによるHTMLソース監査
16. Preview作成
17. GPTによるPreview事前監査
18. 管理者目視確認
19. 管理者OK後にMEDIUM/HIGHを本番反映
20. Step 2導線整備
21. 公開後監査

ユーザーが短い依頼をした場合も、この標準フローを省略せず内部で展開する。

## 4. 自動進行とPreview
- AI編集部は原則としてPreview作成まで自動進行する。
- Preview環境はProductionと分離し、検索エンジンへ未承認コンテンツを流さない。
- Previewサービス名は、実装・接続が確認できるまでは特定サービス名に固定しない。
- 管理者はPreviewで記事全体を目視確認する。
- 管理者NG後は、管理者の問題指摘を要件としてAI側が修正案を設計し、再制作・再監査する。
- Preview目視だけでは承認せず、GPTによるHTMLソース監査を必須とする。
- GPT監査で明確なNGがある場合は管理者へ出さず自動修正へ戻す。

## 5. リスクと公開権限
### LOW: AI自動公開可
以下のような、意味・技術内容・読者判断を変えない明白な修正に限定する。
- 誤字・脱字の明白な修正
- 実在が確認できる壊れた内部リンクの明白な復旧
- 表示内容を変えない整形
- 既に確定済みのメタデータの機械的な修正

LOWであっても、意味が変わる可能性、判断の余地、影響範囲の不明点があればMEDIUMへ上げる。

### MEDIUM/HIGH: 管理者承認必須
新規記事、本文の意味変更、技術情報、記事画像、タイトル、SEO方針、収益導線、カテゴリ構造、削除・統合、安全関連、本番方式などは自動公開しない。

## 6. Gemini障害時
- Geminiによる独立CHALLENGERを通常経路とする。
- 一時障害では再試行する。
- 一時障害が解消しない場合、GPT APIが検証代理を行ってよい。
- GPT代理検証は独立プロバイダ検証ではないため、必ず `⚠️ GPT代理検証・Gemini未確認` 相当の表示・記録を残す。
- GPT代理検証になった案件は、運用ルール上あらかじめ継続許可されている場合は管理者確認を挟まずPreviewまで進めてよい。
- GPT代理検証案件でも、管理者がPreviewを確認しOKすれば公開可能とする。Gemini再検証を公開の絶対条件にはしない。

## 7. 技術情報と公式資料
- メーカー公式サイト、公式マニュアル、公式カタログ、公式FAQ、法令・規格等の一次情報を優先する。
- 最新版がある場合は最新版を優先する。
- 最新資料が存在しない場合、対象機種に対応する旧版公式マニュアルを使用してよい。
- 旧機種の記事では、対象機種との対応が確認できる資料を使う。
- 型式固有の仕様、配線、通信、パラメータ、アラーム、安全、設定手順、注意事項は公式資料で確認できない限り掲載しない。「一般例」と書いて回避しない。
- 一般的な原理・考え方で、型式固有情報ではないものは、根拠と適用範囲を確認したうえで「一般例」「機種により異なる」等を明示して掲載してよい。
- 不明な情報は推測せず「確認できない」と扱う。

### 記事言語と参照資料言語
- 記事の主言語と、参照する公式取扱説明書・技術資料・FAQの言語を原則一致させる。
- 日本語記事では、日本語版の公式取扱説明書・技術資料・FAQを最優先する。
- 英語記事では、英語版の公式 manual / datasheet / technical document / FAQ を最優先する。
- 同一製品・同一改訂に記事言語版と他言語版の両方が存在する場合、記事言語版を優先する。
- 対象言語版が本当に存在しない、または公式サイト上で取得不能な場合のみ、他言語版を補助参照してよい。その場合は使用理由と資料言語を内部監査記録へ残す。
- 機械翻訳されたページより、メーカーが正式公開している対象言語版PDF/HTMLを優先する。
- 「対象言語の資料を見つけられない」と「対象言語の資料が存在しない」を混同しない。存在しないと判断する前に、公式ダウンロード一覧、型式検索、マニュアル名検索、FAQ/技術資料まで再探索する。
- 複数メーカーが同一テーマを扱う場合は、1社で資料が見つからないだけで調査終了せず、記事テーマに適した主要メーカーの公式一次情報を横断確認する。

### 記事内の参照元URL
- 技術的な根拠として使用した主要な公式一次情報は、読者が確認できる形で記事内に参照元URLを提示することを原則とする。
- 参照元URLはメーカー公式ページ、公式マニュアルPDF、公式FAQ、公式技術資料など一次情報へ直接リンクする。
- 検索結果ページや第三者まとめサイトを、一次情報への参照元URLの代替にしない。
- 可能な場合は、資料名・メーカー名・対象機種・改訂情報または公開日とともにリンクを示す。
- PDF直リンクが不安定なメーカーでは、恒久的な公式ダウンロード詳細ページを優先し、必要に応じて資料名・文書番号も併記する。
- 記事本文の可読性を損なわないよう、「参考資料」「公式資料」「出典」等のまとまりで整理してよい。
- 参照元URLを掲載しただけで技術監査を省略してはならない。本文記述と参照資料の内容が一致していることをGPTが確認する。
- 外部リンクはリンク切れ、対象言語、対象機種、改訂整合、`target` / `rel` 等の属性をPreview前に監査する。

## 8. HTML構造
- 新規記事の標準コピー元は `articles/short-ground-leakage-basic.html` とする。
- 制作開始時にGitHub main上のコピー元実ファイルを取得し、ファイル単位で完全コピーして開始する。
- 「参考にする」「似せて再実装する」「同じ雰囲気で新規CSSを書く」は禁止する。
- 原則変更可能なのは、記事タイトル、meta、本文、見出し、記事固有画像、画像alt、関連記事リンク先・タイトル・説明、記事固有ID/anchor、slug、記事固有構造化データ、パンくず内の現在記事情報だけとする。
- ヘッダー、検索、言語切替、パンくず構造、カラム構造、右サイドバー、寄付導線、関連記事UI、会話UI、フッター、共通class、共通CSS、レスポンシブCSSはコピー元からそのまま継承する。
- 共通UIを記事単体で変更しない。変更が必要な場合は共通UI変更案件として別途提案する。
- Preview前にコピー元と新記事のDOM/class/CSS差分をGPTが監査する。
- 詳細は `docs/ai-editorial-article-image-strict-rules.md` を必須参照する。

## 9. 画像ルール
- 記事画像はChatGPTが生成し、Codexは生成担当にしない。
- heroとOGPを基本必須とする。
- 初心者向け新規記事では、本文用の主要図解を原則2〜5枚候補設計する。不要な場合は理由を内部記録する。
- 標準総数は hero 1 + OGP 1 + 本文主要図解2〜5 を基本候補とし、枚数達成自体を目的にしない。
- 画像生成前に「何を画像で理解させるか」を決める。本文が文字だけで説明できることを理由に図解を省略しない。
- 比較・使い分け・原理・構造・動作順序・導入手順・トラブル切り分けは、初心者理解に有効ならAI生成の教材インフォグラフィックを優先してよい。
- `比較表 / 手順 / フローチャート / チェックリスト` という形式だけを理由にHTML/CSS/SVGへ自動振り分けしない。
- 数値・細かな仕様・検索性が重要な情報はHTML表を維持し、概念理解用のAI図解と併用してよい。
- 画像は「装飾」ではなく、画像単体でその節の大筋を理解できる教材として設計する。
- ゴールドスタンダードは `assets/images/star-delta-start-basic/` の既存採用画像セットとする。
- ゴールドスタンダードの品質特性（大見出し、主図、色分け、アイコン、矢印、番号、吹き出し、注意、自然な視線誘導、スマホ可読性）を後続記事へ継承する。
- `雰囲気画像として綺麗` でも `教材として説明力が弱い` 場合は不合格とする。
- キャラクターを含む場合は `assets/images/character-templates/senpai-kouhai-character-template.png` を正本として必ず参照する。
- HTML会話UIでは `assets/images/guide-characters/` の既存画像を使い、生成テンプレートと混同しない。
- hero採用後のキャラクター入り後続画像は、正本テンプレート + 採用heroを参照する。
- 1画像1用途を原則とするが、教材インフォグラフィックでは同一テーマ内の比較・手順・注意を階層化してよい。
- 実在メーカーUI・ロゴ・製品画面を生成画像へ入れない。
- AI生成ビジュアルはWeb向けPNG/WebP等へ整え、簡易SVGを高品質画像として扱わない。
- 詳細は `docs/ai-editorial-article-image-strict-rules.md` と `docs/image-generation-rules.md` を必須参照する。

### 画像品質ゲート
- 生成側は成果物ごとに実画像を視覚確認して自己評価を行う。
- 自己評価の点数だけで採用可否を決めない。
- ゴールドスタンダード画像群と比較し、情報設計・視線誘導・図解密度・親しみやすさ・スマホ視認性で明確に見劣りしないことを確認する。
- 独立IMAGE REVIEWERが、技術的正確性、文字可読性、キャラクター一致、構図、用途一致、記事との関連性、サイト統一感、スマホ視認性、教材としての説明力を評価する。
- HTML組込み後のPreviewでも画像を再評価する。
- 生成側自己評価、ゴールドスタンダード比較、独立IMAGE REVIEWER、Previewレビューの4段階をすべて通過した画像だけを採用候補とする。
- 重大NGが1つでもあれば再制作する。
- 再生成回数自体を固定上限にせず品質を優先する。ただし同じ失敗が続く場合は同一プロンプトを繰り返さず、構図・情報量・プロンプト設計を変更する。
- 技術的誤りが画像で見つかった場合は画像だけ直さず、元記事と公式資料まで戻って整合性を再監査する。
- 最終採用は管理者が記事全体のPreview確認時に画像を含めて判断する。

## 10. 修正ループ
- 通常の自動修正は最大3ラウンドを目安とする。
- 前ラウンドより問題数または重大度が明確に改善している場合のみ最大5ラウンドまで延長できる。
- 同じ重大問題が2回連続で残った場合は、上限を待たず自動修正を停止する。
- 改善が止まった、同じ修正を往復している、証拠不足で決められない場合は `NEEDS_HUMAN` へ送る。
- 回数消化を目的に修正を続けない。

## 11. 管理者判断後
### 修正
管理者の問題指摘を受けてから再開する。具体的な実装方法・文章構成・画像構成はAI編集部が設計し、再監査して再Previewする。

### 却下
- 直ちに同案を無限再生成しない。
- AI編集部は改善案を1回だけ再提案してよい。
- 再提案も採用されなければ `REJECTED/CLOSED` とし、判断履歴を残す。

## 12. キューのライフサイクル
- 24時間以上更新がない進行中案件は `停滞/要確認` として表示する。
- HUMAN_GATE以外で7日間更新がない案件は自動CLOSED対象とする。
- HUMAN_GATE（管理者確認待ち）は日数経過だけでは自動CLOSEDにしない。
- FAILED / ERROR / ESCALATEDは要確認として残す。
- CLOSED / REJECTED / COMPLETED等の履歴は削除せず、完了済みとして折りたたみ・アーカイブ表示する。
- 自動CLOSEDは履歴削除を意味しない。

## 13. 1指示あたりの記事数
- 1回の管理者指示で自動制作する新規記事は最大5本とする。
- 5本を超える要求は分割案件として扱う。
- 複数記事の場合も、各記事が個別に技術・画像・Preview品質ゲートを通過する必要がある。

## 14. Step 1 / Step 2
### 日本語記事 Step 1
AI編集部が記事HTML・画像・監査まで行い、確認用GitHub反映/Preview作成まで自動化する。管理者はPreviewを確認する。

### Step 2
管理者が記事PreviewをOKした後に、トップ・カテゴリ・search-index・sitemap・backlog等の公開導線を整備する。

Step 1とStep 2を混ぜない。管理者OK前にStep 2導線を本番へ追加しない。

## 15. 完成ゲート
Previewへ送る前に最低限以下を満たす。
- 既存記事・重複確認済み
- 必要な公式一次情報確認済み
- 記事言語と主要公式資料の言語一致確認済み
- 他言語資料を補助使用した場合、その理由と資料言語を記録済み
- 主要な公式一次情報の参照元URLを記事内へ適切に掲載済み
- 参照元URLのリンク切れ・対象言語・対象機種・改訂整合確認済み
- 技術監査済み
- SEO監査済み
- `title` / meta description / canonical / robots / OGP / Twitter Card / hreflang / 構造化データ監査済み
- 型式固有・安全情報の根拠確認済み
- 標準コピー元 `articles/short-ground-leakage-basic.html` から制作開始した記録あり
- コピー元と共通UIのDOM/class/CSS差分監査済み
- ヘッダー / 検索 / 言語切替 / パンくず / カラム / 右サイドバー / 寄付導線 / 関連記事 / 会話UI / フッターの継承確認済み
- 全内部リンク・外部リンク属性・画像パス実在確認済み
- h1〜h3階層 / alt / 重複ID監査済み
- 正式ドメインルール適合
- Support this site等の固定リンク適合
- 初心者向け記事で本文図解候補2〜5枚の設計・要否判断済み
- 比較 / 原理 / 手順 / トラブル切り分け等、視覚化効果が高い節の教材図解が十分
- 必要画像が実画像生成済み
- 必要画像がゴールドスタンダード比較を含む4段階品質ゲート通過済み
- 文字ばかりのPreviewになっていないことをGPTが確認済み
- PC/スマホ等のレイアウト確認済み
- Preview環境のnoindex確認済み
- Step 1/Step 2混在なし
- GPTによるHTMLソース監査済み
- GPTによるPreview事前監査済み

未達項目がある場合は `ARTICLE_READY` / `Preview完成` / `NEEDS_HUMAN` と判定しない。

## 16. 判断記録
重要案件では、少なくとも次を記録する。
- 使用したルール版
- コピー元記事
- コピー元差分監査結果
- 主要公式資料
- 主要公式資料の言語
- 記事内に掲載した主要参照元URL
- 他言語資料を補助使用した場合の理由
- EDITOR提案
- CHALLENGER結果とprovider
- Gemini障害/GPT代理の有無
- 技術/SEO/HTML/画像監査結果
- 画像の用途判定（AI生成 / HTML / CSS / SVG）
- ゴールドスタンダードとして参照した既存採用画像セット
- 本文図解候補と採否理由
- 画像ごとの自己評価 / ゴールドスタンダード比較 / IMAGE REVIEWER / Previewレビュー結果
- 修正ラウンド数
- Preview結果
- GPT事前監査結果
- 管理者判断
- 公開/却下/停止理由
