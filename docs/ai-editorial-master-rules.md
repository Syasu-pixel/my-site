# Denkicontrol AI編集部 マスタールール v1.0

## 1. 位置づけ
この文書は、DenkicontrolのAI編集部が記事・画像・Preview・公開判断を扱う際の実行上の正本とする。

既存文書と矛盾した場合の優先順位は次の通り。
1. `docs/ai-governance.md` の安全・法令・人間の権限・秘密情報保護などのPrinciples
2. 本文書 `docs/ai-editorial-master-rules.md`
3. `docs/article-workflow.md`
4. `docs/new-article-checklist.md`
5. `docs/image-generation-rules.md` / `docs/article-type-templates.md` / `docs/reference-notes/**` / `docs/terminology/**`
6. `docs/agents/**` の個別Agent手順

下位文書が上位文書と矛盾する場合は上位を優先し、矛盾を発見したAgentは記録・修正候補として報告する。

## 2. 役割の正本
### ChatGPT / AI編集部
- 記事テーマ・重複・検索意図・既存記事を確認する。
- メーカー公式一次情報を中心に技術調査する。
- 完成済み記事HTMLから最適なコピー元を選定し、完成HTMLを作成する。
- 記事画像を生成する。
- 監査・反証・修正を実行する。
- 日本語記事Step 1では、記事HTML・画像を完成させ、AIがGitHubの確認用ブランチ等へ反映できる運用を標準とする。

### Codex
- 記事本文をゼロから執筆する主担当にしない。
- 配置、静的チェック、リンク・ファイル存在確認、限定的な細修正、Step 2導線整備等を担当する。
- 個別依頼では許可ファイルを最小化し、`docs/agent-runbook.md` に従う。

### 管理者
- Previewで記事全体を目視確認する。
- MEDIUM/HIGHの本番公開を最終判断する。
- NGの場合は「画像イメージが違う」「文章が多く見にくい」等の目的・問題点だけを指示してよい。具体的な修正方法はAI編集部が設計する。

## 3. 記事案件の標準フロー
1. 管理者指示
2. GitHub main・ルール最新版確認
3. 既存記事・検索意図・重複・カニバリゼーション確認
4. 公式一次情報調査
5. EDITOR設計
6. CHALLENGER反証
7. 必要な再設計
8. 最適な既存完成記事をコピー元として選定
9. 記事HTML完成
10. TECHNICAL / SEO監査
11. 必要画像の設計・生成
12. 画像自己評価 + 独立IMAGE REVIEWER
13. HTMLへ採用画像を組み込み
14. HTML・リンク・画像・PC/スマホ等の自動検査
15. Preview作成
16. 管理者目視確認
17. 管理者OK後にMEDIUM/HIGHを本番反映
18. Step 2導線整備
19. 公開後監査

ユーザーが短い依頼をした場合も、この標準フローを省略せず内部で展開する。

## 4. 自動進行とPreview
- AI編集部は原則としてPreview作成まで自動進行する。
- Preview環境はProductionと分離し、検索エンジンへ未承認コンテンツを流さない。
- Previewサービス名は、実装・接続が確認できるまでは特定サービス名に固定しない。
- 管理者はPreviewで記事全体を目視確認する。
- 管理者NG後は、管理者の問題指摘を要件としてAI側が修正案を設計し、再制作・再監査する。

## 5. リスクと公開権限
### LOW: AI自動公開可
以下のような、意味・技術内容・読者判断を変えない明白な修正に限定する。
- 誤字・脱字の明白な修正
- 実在が確認できる壊れた内部リンクの明白な復旧
- 表示内容を変えない整形
- 既に確定済みのメタデータの機械的な修正

LOWであっても、意味が変わる可能性、判断の余地、影響範囲の不明点があればMEDIUMへ上げる。

### MEDIUM/HIGH: 管理者承認必須
新規記事、本文の意味変更、技術情報、記事画像、タイトル、SEO方針、収益導線、カテゴリ構造、削除・統合、安全関連、本番方式などは自動公開しない。

## 6. Gemini障害時
- Geminiによる独立CHALLENGERを通常経路とする。
- 一時障害では再試行する。
- 一時障害が解消しない場合、GPT APIが検証代理を行ってよい。
- GPT代理検証は独立プロバイダ検証ではないため、必ず `⚠️ GPT代理検証・Gemini未確認` 相当の表示・記録を残す。
- GPT代理検証になった案件は記事制作前で一度停止し、管理者または運用ルールに基づく再開判断を待つ。
- 管理者が再開を許可した案件は、Gemini未確認のままPreviewまで進めてよい。
- GPT代理検証案件でも、管理者がPreviewを確認しOKすれば公開可能とする。Gemini再検証を公開の絶対条件にはしない。

## 7. 技術情報と公式資料
- メーカー公式サイト、公式マニュアル、公式カタログ、公式FAQ、法令・規格等の一次情報を優先する。
- 最新版がある場合は最新版を優先する。
- 最新資料が存在しない場合、対象機種に対応する旧版公式マニュアルを使用してよい。
- 旧機種の記事では、対象機種との対応が確認できる資料を使う。
- 型式固有の仕様、配線、通信、パラメータ、アラーム、安全、設定手順、注意事項は公式資料で確認できない限り掲載しない。「一般例」と書いて回避しない。
- 一般的な原理・考え方で、型式固有情報ではないものは、根拠と適用範囲を確認したうえで「一般例」「機種により異なる」等を明示して掲載してよい。
- 不明な情報は推測せず「確認できない」と扱う。

## 8. HTML構造
- 新規記事は、同じ記事タイプ・目的・レイアウトに最も近い完成済み記事をAIが選び、完全コピーを基礎に必要箇所だけ差し替える。
- 上部構造、既存の3カラム構造、キャラクター会話、支援導線、関連記事、既存class、レスポンシブ構造等は原則維持する。
- CSSや構造を記事ごとに独自再設計しない。
- より良い新構造を発見した場合は勝手に導入せず、理由・期待効果・既存記事への影響・移行案を管理者へ提案する。

## 9. 画像ルール
- 記事画像はChatGPTが生成し、Codexは生成担当にしない。
- heroとOGPを基本必須とする。
- 本文画像は内容に応じて1〜4枚を目安とし、説明上不要なら枚数を埋めるために生成しない。
- 標準総数は原則3〜6枚（hero 1 + OGP 1 + 本文1〜4）。記事タイプ上、本文画像が不要と合理的に判断できる場合は理由を記録して例外可とする。
- 本文画像の役割名は記事内容に合わせて選定し、`overview / comparison / flow / check-flow` を無理に全種類作らない。
- キャラクターを含む場合は `assets/images/character-templates/senpai-kouhai-character-template.png` を正本として必ず参照する。
- hero採用後のキャラクター入り後続画像は、正本テンプレート + 採用heroを参照する。
- 1画像1用途。実在メーカーUI・ロゴ・製品画面を生成画像へ入れない。

### 画像品質ゲート
- 生成側は成果物ごとに自己評価を行う。
- 自己評価95点以上を採用候補の条件とする。
- さらに独立IMAGE REVIEWERが、技術的正確性、文字可読性、キャラクター一致、構図、用途一致、サイト統一感を評価する。
- 自己評価とIMAGE REVIEWERの両方を通過した画像だけをPreviewへ組み込む。
- 95点未満またはReviewer不採用の場合は再生成する。
- 再生成回数自体を固定上限にせず品質を優先する。ただし同じ失敗が続く場合は同一プロンプトを繰り返さず、構図・情報量・プロンプト設計を変更する。
- 技術的誤りが画像で見つかった場合は画像だけ直さず、元記事と公式資料まで戻って整合性を再監査する。
- 最終採用は管理者が記事全体のPreview確認時に画像を含めて判断する。

## 10. 修正ループ
- 通常の自動修正は最大3ラウンドを目安とする。
- 前ラウンドより問題数または重大度が明確に改善している場合のみ最大5ラウンドまで延長できる。
- 同じ重大問題が2回連続で残った場合は、上限を待たず自動修正を停止する。
- 改善が止まった、同じ修正を往復している、証拠不足で決められない場合は `NEEDS_HUMAN` へ送る。
- 回数消化を目的に修正を続けない。

## 11. 管理者判断後
### 修正
管理者の問題指摘を受けてから再開する。具体的な実装方法・文章構成・画像構成はAI編集部が設計し、再監査して再Previewする。

### 却下
- 直ちに同案を無限再生成しない。
- AI編集部は改善案を1回だけ再提案してよい。
- 再提案も採用されなければ `REJECTED/CLOSED` とし、判断履歴を残す。

## 12. キューのライフサイクル
- 24時間以上更新がない進行中案件は `停滞/要確認` として表示する。
- HUMAN_GATE以外で7日間更新がない案件は自動CLOSED対象とする。
- HUMAN_GATE（管理者確認待ち）は日数経過だけでは自動CLOSEDにしない。
- FAILED / ERROR / ESCALATEDは要確認として残す。
- CLOSED / REJECTED / COMPLETED等の履歴は削除せず、完了済みとして折りたたみ・アーカイブ表示する。
- 自動CLOSEDは履歴削除を意味しない。

## 13. 1指示あたりの記事数
- 1回の管理者指示で自動制作する新規記事は最大5本とする。
- 5本を超える要求は分割案件として扱う。
- 複数記事の場合も、各記事が個別に技術・画像・Preview品質ゲートを通過する必要がある。

## 14. Step 1 / Step 2
### 日本語記事 Step 1
AI編集部が記事HTML・画像・監査まで行い、確認用GitHub反映/Preview作成まで自動化する。管理者はPreviewを確認する。

### Step 2
管理者が記事PreviewをOKした後に、トップ・カテゴリ・search-index・sitemap・backlog等の公開導線を整備する。

Step 1とStep 2を混ぜない。管理者OK前にStep 2導線を本番へ追加しない。

## 15. 完成ゲート
Previewへ送る前に最低限以下を満たす。
- 既存記事・重複確認済み
- 必要な公式一次情報確認済み
- 技術監査済み
- SEO監査済み
- 型式固有・安全情報の根拠確認済み
- HTML構造チェック済み
- 全内部リンク・画像パス実在確認済み
- 正式ドメインルール適合
- Support this site等の固定リンク適合
- 必要画像が品質ゲート通過済み
- PC/スマホ等のレイアウト確認済み
- Step 1/Step 2混在なし

未達項目がある場合は `ARTICLE_READY` と判定しない。

## 16. 判断記録
重要案件では、少なくとも次を記録する。
- 使用したルール版
- コピー元記事
- 主要公式資料
- EDITOR提案
- CHALLENGER結果とprovider
- Gemini障害/GPT代理の有無
- 技術/SEO/画像監査結果
- 修正ラウンド数
- Preview結果
- 管理者判断
- 公開/却下/停止理由

内部の非公開思考過程そのものを保存対象にはしない。
