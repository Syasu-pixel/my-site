# Denkicontrol AI Governance v0.1

## 1. 目的
Denkicontrol を、電気・制御・FA・空圧の技術情報を蓄積する大規模な専門メディアへ成長させ、将来は読者同士が知識・経験を共有し、互いに問題解決を助け合える技術コミュニティへ発展させる。

AI は単なる記事生成器ではなく、調査・企画・制作・反証・監査・改善・運用を分担するチームとして使う。ただし、一つのAI、一つのモデル、一つの判断を無条件に正しいものとして扱わない。

## 2. この文書自身も再検討対象
この文書は永久不変の規則ではない。AI能力、サイト規模、検索環境、読者行動、収益構造、運用実績の変化に応じて再評価する。

ただし、安全、法令、技術的根拠、人間の承認権など強い制約を緩和する変更は、通常の運用改善より慎重に扱い、人間の承認を必要とする。

## 3. ルールの3階層
### Principles / 原則
安全、法令、技術的根拠、読者利益、透明性など。原則としてAIだけで緩和しない。

### Operating Policies / 運用方針
記事制作手順、初心者から実務への導線、キャラクター運用、曜日別運営、承認フローなど。従うが、実績に基づき定期的に再評価できる。

### Tactics & Hypotheses / 戦術・仮説
タイトル、画像枚数、内部リンク方法、SEO施策、モデル割当など。データと反証により積極的に変更する。

## 4. サイトの上位原則
- 読者が技術を理解し、安全に次の判断へ進めることを優先する。
- メーカー公式資料、仕様書、図面、法令・規格、現場ルールを優先する。
- PV・順位・売上だけを目的に技術情報の信頼性を損なわない。
- 同じ検索意図の記事、重複記事、表現だけを変えた類似記事を量産しない。
- 既存記事を資産として活用し、新規作成前に重複・カニバリゼーション・統合可能性を確認する。
- 収益化のために技術情報の中立性や将来のコミュニティ価値を意図的に損なわない。

## 5. AIチームの基本構造
AIの役割はモデル名や提供会社に固定しない。能力評価によりモデルを交換できる。

### EDITOR
検索データ、既存記事、サイト構造、読者価値から次の作業候補を選定し、目的・根拠・期待効果・リスクを提示する。

### BUILDER
承認された方針に基づき記事HTML、必要なコード、構造変更等を実装する。

### CHALLENGER
提案に賛成することを目的としない。重複、技術的誤り、検索意図のずれ、回帰、短期最適化、証拠不足など、提案が間違っている可能性を独立して探す。

### TECHNICAL REVIEWER
電気・制御・FA・空圧の技術的正確性、安全性、断定表現、公式資料との整合性を監査する。

### SEO REVIEWER
検索意図、CTR、既存URLとの競合、内部リンク、構造、Google/Bingの反応を監査する。

### IMAGE REVIEWER
画像の技術的正確性、公式キャラクターとの一致、構図、可読性、サイト統一感を独立監査する。

### REVIEWER / ADJUDICATOR
提案、反証、各監査結果を比較し、ADOPT / REVISE / HOLD / REJECT を判定する。

## 6. 多様性と多数決禁止
- 複数AIの利用目的は票数を増やすことではなく、異なる失敗傾向・視点を得ることにある。
- 多数決だけで重要判断を決めない。
- 反対意見を消さず、重要な異論は判断記録に残す。
- 同一モデルを複数役に使う場合でも、役割・評価基準・入力を分離する。
- OpenAI、Anthropic、Google等の提供会社やモデルは固定メンバーではなく、性能・費用・信頼性に応じて変更できる。

## 7. AI間で意見が割れた場合
AIだけで十分に解消できない重要な対立はユーザーへエスカレーションする。

エスカレーション時は最低限、以下を示す。
- 何を決める必要があるか
- 各案
- 各AIの結論
- 根拠
- 主な反論
- リスク
- 推奨案
- 判断後にルール化できる可能性

同種の判断が蓄積した場合は、ユーザー判断を運用方針へ反映する。十分な実績が得られれば、専用の裁定AIへ委譲することも再検討する。

## 8. GitHub権限と人間確認
AIがGitHub上で変更を進められる仕組みを構築する。ただし当面は人間確認ゲートを設ける。

- AIは確認用ブランチへの変更、コミット、PR作成まで実行可能にする。
- 本番公開につながる変更は、ユーザーが内容を確認した後に進める。
- 記事・ページ変更では、最終的に実ページに近いPreview URLを人間が目視確認できる環境を構築する。
- `main` は本番基準とし、PreviewとProductionを分離する。
- 現在のGitHub Pages / IndexNow挙動を考慮し、Preview作成を本番公開と同義にしない。

## 9. 新規記事テーマの自律選定
AIチームは新規記事テーマを自律的に提案・選定できる。

新規作成前に最低限確認する。
- 既存記事との検索意図重複
- 類似記事・カニバリゼーション
- 既存記事の追記や改訂で解決できないか
- GSC / Bing等の需要シグナル
- サイト内の知識ギャップ
- 初級→中級→上級→実務の導線上の役割
- 技術的根拠を十分確保できるか

記事本数を増やすこと自体を成功指標にしない。

## 10. 新規記事の当面の標準フロー
1. テーマ候補選定
2. 重複・検索意図・既存記事確認
3. 技術調査・根拠収集
4. EDITOR提案
5. CHALLENGER反証
6. 必要なら再設計
7. HTML本文完成
8. TECHNICAL / SEO監査
9. 画像生成
10. 画像品質ゲート
11. 独立IMAGE REVIEWER監査
12. HTMLへ画像組み込み
13. HTML・リンク・レイアウト等の自動検査
14. Previewブランチ / PRへ反映
15. Preview URL発行
16. ユーザー目視確認
17. ユーザーの公開OK
18. Production / mainへ反映
19. sitemap、検索index、カテゴリ、内部リンク等の公開導線確認
20. Google / Bingへの公開反映・通知
21. 公開後の検索反応を継続観測

## 11. 人間承認の現在地
当面は以下を人間ゲートとして残す。
- AI間で解消できない重要な対立
- 本番公開前のPreview確認
- 記事画像の最終採用
- 強い原則や安全制約の緩和
- 大きな事業方針・収益化方針

AI性能と運用実績が十分蓄積した場合、低リスク作業から承認範囲を再評価できる。

## 12. 判断記録
重要判断では可能な限り以下を記録する。
- Decision
- Date
- Proposal
- Evidence
- Counterarguments
- Rejected alternatives
- Verdict
- Confidence
- Human decision if any
- Reconsideration triggers

採用されなかった反対意見も、将来の再評価に価値がある場合は残す。

## 13. AI間の可視性
ユーザーがAIチームの動きを監査できるようにする。

表示・記録対象は、提案、使用した根拠、反証、結論、ツール実行、変更ファイル、テスト結果、裁定、費用・性能指標等とする。モデル内部の非公開思考過程を保存・表示することを要件にはしない。

## 14. AIモデルと費用の評価
各AIの最低限の有料利用を許容範囲とし、より高いプランが費用対効果に優れる場合はAIチームから提案できる。

毎週月曜日の運営レビューでは必要に応じて以下を評価する。
- 新モデル・主要アップデート
- API / プラン / 価格変更
- コーディング、技術監査、反証、SEO、画像等の能力
- 外部評価やベンチマーク
- Denkicontrol内部での実績
- エラー率・人間採用率
- コストと品質改善幅

ネット上の評判だけでモデルを交代させず、Denkicontrolの実タスクで評価する。

## 15. 収益化
Denkicontrolは大規模な専門メディア事業を目指し、仕事獲得にもつなげる。将来は技術者同士が情報交換し、問題解決を助け合えるコミュニティへ発展させる。

具体的な収益化ルールは別途ユーザーと策定する。当面の原則は、収益のために読者価値、技術的信頼性、中立性、コミュニティ価値を意図的に損なわないこととする。

## 16. 既存ドキュメントとの関係
既存の `docs/denkicontrol-site-strategy.md`、`docs/agent-runbook.md`、`docs/article-workflow.md`、`docs/new-article-checklist.md`、`docs/image-generation-rules.md` 等は引き続き有効とする。

この文書は複数AIによる運営・権限・反証・人間承認・再検討の上位方針を追加する。既存文書との矛盾を発見した場合、AIが独断で消すのではなく、矛盾を記録して改訂案を提示する。

## 17. v0.1の範囲
v0.1ではルールを完成形にしない。まず小規模な実運用で検証する。

初期実験は EDITOR → CHALLENGER → REVIEWER → HUMAN を基本とし、既存記事または新規記事1件で試す。その後、Technical / SEO / Image / Builder、GitHub Preview、GSC / Bing、曜日別自動運営を段階的に接続する。
