# AI検索・引用最適化ルール

この文書は、denkicontrol.com の新規記事作成・既存記事改善・検索分析で、通常のSEOに加えて Bing / AI検索から引用されやすく、かつ人間にも読みやすい記事を作るための共通ルールを定義する。

検索実績データの取得経路は `docs/search-data-acquisition-rules.md` を正本とする。取得経路について本書と正本が矛盾する場合は `docs/search-data-acquisition-rules.md` を優先する。

## 基本方針

- AI向けだけの不自然な文章にはしない。人間の読者にとって分かりやすいことを最優先する。
- SEO評価だけでなく、Bing Webmaster Tools の検索実績と、確認可能なAI引用実績もサイト成長の判断材料にする。
- Googleで弱い記事でも、Bing検索またはAI引用で強い場合は一律に低評価・削除対象にしない。
- メーカー仕様、規格、数値、機種固有情報、安全上の注意は、従来どおりメーカー公式の最新一次情報を優先する。
- 公式情報で確認できない内容は推測で断定しない。

## 記事作成・改善ルール

- 各記事は、検索ユーザーの主要な疑問に対する短く明確な答えを冒頭付近に置く。
- 「〇〇とは」「〇〇の違い」「なぜ〇〇するのか」「〇〇の選び方」など、質問と回答の対応が分かりやすい見出しを必要に応じて使う。
- 定義、違い、原因、判断基準、注意点は、1〜3文を単独で引用しても意味が通じるように書く。
- 結論を不必要に引き延ばさず、結論→理由→具体例の順で説明できる箇所はその順を優先する。
- 比較、手順、条件分岐、選定基準は、表・箇条書き・短い段落を適切に使い、情報の関係を機械にも人間にも読み取りやすくする。
- 初心者向け記事でも用語説明だけで終わらせず、基本概念→仕組み→実務でどう使うか、まで自然につなげる。
- 関連記事は学習順序や概念のつながりが分かるように内部リンクで結ぶ。SEO目的だけの無理なリンクは作らない。
- 同じ意味のキーワードを不自然に反復しない。キーワード詰め込みやAI引用狙いだけの冗長なFAQ量産をしない。
- 既存のサイト構造、3カラム、キャラクター会話、支援導線、画像説明などの既定記事構造を壊さない。

## 記事設計・最終監査でのAI引用品質ゲート

この確認は、新規記事作成と既存記事の全面刷新・内容更新の両方に適用する。AI向けの別記事を作るのではなく、人間向けの技術品質を高めた結果として機械にも引用・再利用しやすい状態を作る。

### 設計・本文作成時
- 記事の主要な疑問を明確にし、その疑問への答えが本文中で迷わず特定できる構成にする。
- テーマに必要な範囲で「何か」「なぜそうなるか」「どう使う・どう確認するか」「何に注意するか」を整理する。すべての記事へ機械的に同じ見出しを追加しない。
- メーカー公式資料で確認した事実・仕様と、Denkicontrolによる現場経験・実務上の解釈・補足を混同しない。読者が根拠の性質を誤認しない書き方にする。
- 定義、原因、違い、判断基準、重要な注意点は、前後の長文を読まなくても必要な文脈が分かる文章単位を意識する。ただし不自然なFAQ化や断片文の量産はしない。
- 内部リンクは単なる関連記事数の確保ではなく、前提知識、関連概念、次の判断・確認に必要な知識をつなぐ目的で選ぶ。

### 最終監査時
- 本文だけを読んでも、記事の主要な疑問への回答材料が揃っているか。
- 重要な技術的主張について、メーカー公式情報・確認済みreference-notes・Denkicontrol独自の実務補足の関係が曖昧になっていないか。
- 必要なテーマでは、定義だけで終わらず、原理・理由・実務での意味・注意点まで適切に説明できているか。
- 重要な意味が画像内だけに残っていないか。詳細は本書の「画像内技術情報のHTML保持ルール」に従う。
- 前提知識と次に必要な関連知識への導線があり、同一テーマの無関係なリンクをSEO目的で増やしていないか。
- 主要な定義・原因・比較・判断基準が、AI引用を意識するあまり不自然な文章やキーワード反復になっていないか。

この品質ゲートはAI引用数を保証するものではない。検索・AIサービスのアルゴリズムを推測して文章を作るのではなく、正確で根拠が明確な技術情報を、読者にも機械にも理解しやすい形で蓄積するために使用する。

## 著者・発行主体の構造化データ接続ルール

- 新規記事作成および既存記事刷新では、Article系の構造化データを使用する記事について、著者と発行主体の関係を明示する。
- `author` は Denkicontrol の公開運営者プロフィールに定義した Person を参照し、同一人物を示す `@id` は `https://denkicontrol.com/profile/#operator` に統一する。
- `publisher` は Denkicontrol の Organization を参照し、`@id` は `https://denkicontrol.com/#organization` に統一する。
- 記事側の `author` とプロフィール側の Person は、名前だけでなく同一 `@id` で接続する。人間向けには共通フッター等から「運営者・編集方針」ページへ到達できる導線を維持する。
- プロフィールには公開可能な実務経験・専門領域・編集方針のみを記載し、構造化データのために実名、勤務先、住所その他の不要な個人情報を追加しない。
- 構造化データへ記載する内容は、公開ページ上で確認できる内容と矛盾させない。検索エンジンやAIだけを対象にした架空の経歴・資格・専門性を追加しない。
- 既存全記事への一括書換えは禁止する。既存記事は各記事の刷新・内容更新時に1記事ずつ適用し、その記事に必要なbaseline・台帳・保全検査を正規手順で更新する。
- 構造化データを追加・変更するために、既存のbaseline検査、SEO保持検査、記事統合検査などの安全装置を無効化・迂回しない。
- Article構造化データが既に存在する記事では、既存のheadline、description、image、mainEntityOfPage等を壊さず、重複するArticle JSON-LDを無計画に追加しない。
- Article構造化データがない記事では、記事刷新時に既存テンプレート・SEO構造との整合を確認してから導入する。

### 最終監査
- Articleの `author.@id` が公開プロフィールの Person `@id` と一致しているか。
- `publisher.@id` が Denkicontrol の Organization `@id` と一致しているか。
- 構造化データの経歴・専門領域が公開プロフィール本文と矛盾していないか。
- 同一記事に競合・重複するArticle構造化データがないか。
- 記事更新に伴うbaseline・台帳・CIが正規手順で通っているか。

## 画像内技術情報のHTML保持ルール

- 重要な技術情報を画像だけに閉じ込めない。
- 本文画像が、技術的事実、動作原理、因果関係、構成、判断基準、安全上の注意を説明している場合、その意味は本文HTMLでも理解できる形で記述する。
- 画像内容を本文へ逐語的に重複させる必要はない。本文は「何が重要か・なぜそうなるか・何を確認するか」を説明し、画像は配線、構造、信号経路、動作順序、比較などを視覚化する役割とする。
- 画像をAIや検索システムが解析しない場合でも、記事本文だけで主要な技術的意味が失われない状態を完成条件とする。
- `alt` はアクセシビリティを主目的とし、画像が何を示すかを簡潔かつ正確に記述する。AI引用狙いのキーワード詰め込みや、画像内全文の転記場所として使用しない。
- `figcaption` は人間の理解に役立つ場合に使用する。本文と同じ説明を繰り返すためだけに追加しない。
- `display:none`、画面外配置、透明文字等を使って、AI・検索エンジンだけを対象にした非表示説明文を追加しない。
- 記事監査時は「この画像を解析できなくても、本文HTMLだけで重要な技術内容を理解できるか」を確認する。
- 画像と本文の技術的説明が食い違う場合は公開・採用しない。メーカー公式情報および確認済みreference-notesを基準に整合させる。

## 月曜日の調査・企画への反映

月曜調査では、`docs/search-data-acquisition-rules.md` に従って取得・保存された Google Search Console と Bing Webmaster Tools の実データを確認する。公式APIルートが未実装または一時障害中の場合は、取得済みデータの範囲を明示し、欠損を推測で補わない。

Bing Webmaster Tools では、少なくとも以下を優先して確認する。

- 検索クエリ
- クリック
- インプレッション
- CTR
- 日付推移
- 取得可能なページ・URL情報

分析時は、次を候補化する。

- Googleでは弱いがBingで伸びているクエリ・テーマ
- Bingでインプレッションが伸びているがクリックを十分取れていないテーマ
- CTRが高く、追加記事や関連記事展開の余地があるクエリ
- AI引用が確認できた記事・質問テーマ
- Google/Bing双方で需要が確認できるのに既存記事で十分答えられていないテーマ

Bingの実データが一時的に取得できない場合は、推測値で埋めず「Bingデータ未取得」と明記し、Google側だけで最終判断したように扱わない。

## 金曜日のSEO・検索パフォーマンスへの反映

- Google Search Console と Bing Webmaster Tools は別々に評価し、最後に横断比較する。
- Google側では表示回数、クリック、CTR、平均掲載順位、インデックス状況を確認する。
- Bing側では取得可能な検索クエリ、クリック、インプレッション、CTR、日付推移を確認する。
- Bingで強いページを、Googleで弱いという理由だけで低評価にしない。
- AI引用実績が確認できる場合は、引用されたページとテーマを記録し、新規記事・既存記事改善・内部リンク改善へ反映する。
- 実データがない場合は大規模変更を行わない。

## AI引用実績の扱い

- AI引用数は検索クリックの代替ではなく、独立した評価指標として扱う。
- 引用されたからといって、その文体を機械的に全記事へコピーしない。
- 引用ページに共通する構造、回答の明確さ、一次情報の使い方、見出し設計、内部リンクを比較し、再現性のある要素だけを標準ルールへ戻す。
- AI検索サービスごとに評価傾向が異なる可能性があるため、Bingの結果をGoogleや他AI検索へそのまま一般化しない。

## 外部データ接続の注意

- 検索実績の標準取得経路は `Google Search Console API / Bing Webmaster API -> GitHub Actions -> Supabase -> ChatGPT` とし、詳細は `docs/search-data-acquisition-rules.md` に従う。
- **GSC Wizard は定例集計・検索確認の標準ルートとして使用しない。** 以前GSC Wizardを使っていた運用へ、新しいチャットが自動的に戻らないようにする。
- Windsor.ai 等の第三者連携も恒久標準とはせず、管理者が明示した一時的な補助用途に限る。
- 第三者サービスの無料枠を使い切るたびに別サービスへ乗り換える運用を採用しない。
- APIキー、OAuth secret、refresh token、APIキー入りURL等を記事、GitHub、公開ログ、PR本文へ保存しない。
- `ThrottleIP`、quota、認証エラー等が発生した場合、短時間に再読込や再実行を連打しない。
- データ取得エラー時は設定ミスと断定せず、公式APIの状態、認証、取得期間、選択フィールド、quota、仕様変更を確認して切り分ける。
