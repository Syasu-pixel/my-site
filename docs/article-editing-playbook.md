# 新規記事・既存記事更新の実作業手順

この文書は共通ひな形導入後の作業順をまとめる。最初に [ルール確認の入口](rules/README.md) の読了手順を実行する。安全・技術品質・公開権限は [マスター](ai-editorial-master-rules.md)、現在の公開状態は [移行記録](site-template-migration-status.md) が正本。本書は停止中のAI編集部や有料APIを再開する指示ではない。

## 1. 最初に作業を分ける

|依頼|開始時の判断|
|---|---|
|新規記事|既存記事との重複、言語、記事タイプ、利用できる部品と例外を確認し、下記の新規登録へ進む|
|本文・title・meta・見出しの更新|[日付ガード](article-update-date-guard.md) → [検索データ事前確認](article-search-data-precheck-override.md) → 一次資料 → 差分編集|
|誤字・リンク・表示だけの保守|検索意図・技術内容を変えない範囲を明示。検索データ確認の保守例外を適用し、内容更新日を自動更新しない|
|ひな形の変更|利用ページを列挙し、共通部品の正本を変更。記事本文を一括改稿しない|

通常のChatGPTからも同じ入口を使う。GitHubを取得できない場合は未確認と明記し、過去の会話だけで最新版を読んだことにしない。

## 2. 編集する場所

|変更したいもの|編集元・参照先|
|---|---|
|本文・記事固有タイトル・説明・関連記事の行き先|リポジトリ内の記事HTML。公開サイトやcandidate/review出力をコピーして編集元に戻さない|
|公開用の固定ヘッダー|`.github/site-shells/ui-proposal/`。旧ソース整合用のcomponentsとは区別する|
|フッター・広告表記|`.github/site-shells/components/`。広告文はaffiliate-disclosure.njkが単一正本|
|右欄・追従目次|`.github/article-components/sidebar/` の部品とページ別役割台帳|
|関連記事の枠・評価欄|`.github/article-components/end/`。日本語だけ評価あり、固有slugと既存投票処理を保持|
|ヒーローの共通構造・専用CSS|[ヒーロー手順](article-hero-templates.md) のhero.njkとCSSプロフィール。タイトル等の固有内容は記事HTML|

[shell手順](site-shell-implementation.md) と [統合手順](article-components-integration.md) を併読する。記事HTMLは本文の編集元でもあり、全体を編集禁止の生成物と扱わない。逆に共通部品を各記事へ直接書き足して運用しない。

## 3. 新規記事 — Step 1

1. 最新main、未完了PR、依頼範囲を確認。同じ種類の既存記事を構造参照にし、利用可能なひな形を選ぶ。設計シリーズ、工具、キャリア、相談等の専用構成を通常記事へ強制しない。
2. 検索データ・一次資料・記事タイプ・画像の現行ルールに沿って固有内容を作成。コピー元のURL、slug、言語リンク、画像、SEO値を残さない。画像枚数はマスター第9節に従い、旧「5枚固定」を適用しない。
3. 次の登録を**同じPR**で照合する。登録用の一括コマンドは現時点では用意されていないため、既存スキーマと生成器を確認して対象分だけ追加する。

|台帳|新規記事で必要な対応|
|---|---|
|`.github/site-shells/manifest.json`|output、articleFile、headerTemplate、footerTemplateと最終ソースのbaselineSha256を登録。言語・相対リンクを確認|
|`.github/article-components/integration.json`|targetsへ追加。必要な用途別設定も登録|
|`.github/article-components/site-inventory.json`|追加HTMLのpath・gitBlobと必要属性を登録|
|`.github/article-components/sidebar/all-pages.json`|既存pages.jsonとの重複を避け、右欄のカード役割・保持順・目次・境界幅を対象構造から登録|
|`.github/article-components/end/all-preservation-oracle.json`|新記事の関連記事・評価等の期待値を元ソースから独立確認して追加|
|`.github/article-components/hero/manifest.json`|利用可能な構造ならtargetsとpageVariantsに登録。非対応構造を黙って変換しない|
|`.github/article-components/hero/css-bindings.json`|対象記事のCSS対応を登録。既存共有CSSの意図した変更を初期化で上書きしない|

4. 検査・workflow内の固定件数も確認する。現行実装には288記事、309 HTML等の初回移行件数を固定した検査がある。登録だけで新規記事対応が完了したとは扱わない。新旧の対象集合と追加URLを照合して必要な期待件数・集約を更新し、欠落・重複を拒否する検査は維持する。日英や例外の件数を一律加算しない。
5. 日本語の評価slug・backend許可・集計登録は [評価ルール](article-feedback-rules.md) に従う。英語には評価欄を追加しない。実在する翻訳先だけを設定する。
6. 下記の生成・検査を実施し、PC・スマホ・タブレットの確認用表示を用意する。Step 1ではトップ・カテゴリ・検索インデックス・sitemap・backlogの公開導線を変更しない。台帳登録は生成に必要な登録であり、公開導線追加とは区別する。

## 4. 既存記事の内容更新

1. 日付ガード、凍結状態、履歴、検索データ、必要な一次資料を確認。実質更新と保守を区別する。
2. 最新の記事HTMLの必要な部分だけ編集し、共通部品・専用レイアウト・URL・評価slugを保つ。新しい見出しは重複しないアンカーと目次の移動先を確認する。
3. **期待差分を先に記録してから検査基準を更新する。** 対象記事のshell baselineSha256、inventory gitBlob、関連記事oracleのsourceSha256等を点検する。右欄の内容・順序変更なら役割台帳、ヒーローCSS変更ならbindings/例外指紋も点検する。本文だけの更新で無関係な部品採用ハッシュを変更しない。
4. ハッシュは最終編集元の実バイトから計算する。gitBlobはGit blob形式、baselineSha256はSHA-256であり混同しない。更新対象・旧新値・意図した差分をPRへ記録。生成された変更後画面を無条件で新基準にして失敗を消さない。
5. 内容更新日と公式資料確認日をそれぞれ実際の作業に合わせる。titleや説明等を変えた場合は検索インデックス等の影響も確認する。既存記事更新を新規記事のStep 2追加として扱わない。

## 5. 生成・検査・公開

正規入口は `scripts/build-integrated-review.mjs`。具体的な実行コマンドは [統合手順](article-components-integration.md) と [ヒーロー手順](article-hero-templates.md) に従う。

- 共通shell整合 → 最新ソースから統合生成 → 本文/SEO/リンク/画像/目次/関連記事・評価の保全検査 → 公開候補検査の順で実行する。
- 意図した内容変更は変更前後で差分を確認し、ひな形生成がその内容を欠落・上書きしていないことを別に確認する。内容変更なのに旧画面との差分0を要求しない。
- 変更記事、影響する共通部品利用先、特殊構成と境界幅を検査する。必須CIは通すが、変更や失敗がないのに同じ全件検査を繰り返さない。
- candidateが公開候補、reviewはnoindex・送信隔離付きの確認用。reviewを本番へ配信しない。Previewサービス名は固定せず、現行生成経路と実際に開けるURLを確認する。スマホへlocalhostを案内しない。
- 必要な公開承認はマスターに従う。既に受けた対象範囲の承認を繰り返し求めない。マージとPages成功、実サイト反映を別々に確認し、公開後のURLと結果を報告する。

## 6. 新規記事 — Step 2の導線

管理者のPreview OK後に進む。通常の基本導線は、対象言語のトップ新着、カテゴリ、検索インデックス、ルートsitemap、backlog。**Step 2-Aでもトップ新着を対象とする**。旧「index.html/en/**を一律変更禁止」と両立させようとしない。記事本文と画像は変更せず、日英対応を作った際のlanguage-menu/hreflang更新は対象を明示した限定差分にする。

- 新着は日英とも7件、トップカテゴリ棚は4件。英語Popularは10件。新着更新とカテゴリ棚・人気記事の入れ替えを混同しない。
- 棚の追加・入れ替えは管理者の明示依頼時だけ。新記事追加で5件目を足さない。
- 既存記事へ関連記事を追加するStep 2-Bは必要な場合だけ分離し、原則1記事ずつ。生成前の関連記事固有データと保全基準を確認する。
- 非運用の `seo/sitemap.xml` は変更しない。導線の有無、重複、対象言語、翻訳先実在を確認する。

この節は、マスター第14節と通常の新着運用を具体化し、下位文書のStep 2-Aの一律禁止・新着6件という記述を置き換える。公開承認や対象外本文の変更許可を広げない。

## 7. 完了報告

確認したcommitと適用ルール、対象URLと記事タイプ、編集元と登録先、意図した差分、生成・検査結果、未確認範囲、Preview、承認範囲、公開状態を短く残す。未登録・未検査・未公開を「完了」とまとめない。
