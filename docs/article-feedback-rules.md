# 記事評価カード運用ルール（article feedback rules）

## 目的
- 記事末尾の「この記事は役に立ちましたか？」を全記事で安全に再利用できる共通部品として扱う。
- 👍 / 👎 の結果を記事単位で集計し、`/admin/` の運営ダッシュボードで改善優先度を確認できるようにする。
- 記事ごとの個別実装・二重送信・同一ブラウザからの多重投票・集計先の混同を防ぐ。

## 正式な初期実装
- 最初の本番実装は `articles/plc-drilling-line-design-project-01.html`。
- 共通フロント処理は `assets/js/article-feedback.js`。
- 保存先は Supabase `public.article_feedback`。
- ブラウザからDBへ直接書き込まず、Supabase Edge Function `article-feedback` を経由する。
- 運営側の確認先は `/admin/` の記事評価ダッシュボード。

## 共通UIルール
- 原則として記事本文・次回案内等の後、`あわせて読みたい記事` / `related-grid` より前に配置する。
- 見出しは `この記事は役に立ちましたか？` を基本とする。
- 選択肢は `👍 役に立った` / `👎 役に立たなかった` の2択を基本とする。
- 投票送信中だけ一時的に操作不可にしてよい。
- 投票確定後は両ボタンを無効化し、選択済み側だけ選択状態を残す。
- 投票確定後の表示は `投票済みです。ご協力ありがとうございます。` 相当とする。
- 投票済みボタンのカーソルは通常の矢印（`default`）とし、`wait` / ぐるぐる待機カーソルを残さない。
- PC / スマホ双方でレイアウトが崩れないことを確認する。

## 1ブラウザ・1記事・1票ルール
- 厳密な本人認証ではなく、匿名のブラウザ識別キーを使う簡易アンケートとして運用する。
- 同一ブラウザ環境では、同一記事への投票は最初の1票で確定する。
- 日数経過だけでは再投票可能にしない。
- 2回目以降は票を追加・上書きしない。
- ブラウザデータ削除、シークレットモード、別ブラウザ、別端末では別票になり得る。これは簡易アンケートの仕様として許容する。
- サーバー側でも `(article_slug, voter_key)` の一意性を保持し、フロントだけに多重投票防止を依存しない。

## article_slug ルール
- `article_slug` は記事を識別する安定IDとする。
- 原則として記事HTMLのファイル名から `.html` を除いた値と一致させる。
  - 例: `articles/sensor-2wire-3wire-basic.html` → `sensor-2wire-3wire-basic`
- 同一記事の改稿ではslugを変更しない。
- 別記事で同じslugを再利用しない。
- **第1回記事の `plc-drilling-line-design-project-01` を他記事へそのままコピーしない。**
- 共通JSを複数記事へ展開する際は、記事HTML側のdata属性・設定値等からその記事固有slugを渡す構造にする。共通JS内部へ1記事のslugを固定したまま横展開しない。
- backendの許可記事リスト / 記事登録機構がある場合は、新記事公開時にそのslugも登録・確認する。

## 送信データ契約
Edge Functionへ送る基本項目は以下とする。

- `article_slug`: 記事固有slug
- `vote`: `helpful` または `not_helpful`
- `voter_key`: 匿名ブラウザ識別キー（UUID形式）

個人名、メールアドレス、会員ID等の個人情報を記事評価のためだけに収集しない。

## フロント実装ルール
- 投票処理は原則 `assets/js/article-feedback.js` に集約する。
- `site-search.js` 等、別用途の共通JSへ投票処理を重複実装しない。
- 1つのボタンに複数の投票イベントハンドラを付けない。
- `localStorage` が使えない環境では、ページ内メモリ等へ安全にフォールバックしてよい。
- ブラウザ識別キーと記事別の投票済み状態は別キーで管理する。
- Edge Functionから `already_voted` 相当が返った場合は失敗表示にせず、既存票を保持して `投票済み` 状態へ遷移する。
- 投票確定後は再送信しない。
- JSを更新した場合は、記事HTML側の `article-feedback.js?v=...` 等のキャッシュキーも更新し、旧JSが残らないようにする。

## Supabase / セキュリティルール
- ブラウザへ `service_role` / secret key を絶対に埋め込まない。
- ブラウザで使うのは公開用途の publishable key のみとする。
- DB書き込みは Edge Function 側で行う。
- Edge FunctionのCORSは正式ドメイン `https://denkicontrol.com` / `https://www.denkicontrol.com` と、確認が必要な承認済みPreview originだけを扱う。
- `article_feedback` はRLSを有効にしたまま運用する。
- backendがDBへ保存するために必要な権限（`INSERT` / `SELECT` 等）が実際に付与されていることを確認する。
- secret / service-roleをGitHubの公開HTML・公開JS・ログ・PR本文へ出さない。

## 管理ダッシュボード集計ルール
- 集計の主キーは `article_slug` とする。
- 記事ごとに以下を確認できる状態を維持する。
  - 総投票数
  - 👍 役に立った
  - 👎 役に立たなかった
  - 好評価率
  - 最新投票日時
- 新しい記事slugが追加された場合でも、最低限slug自体を表示して「どの記事の票か」が分からなくならないようにする。
- 表示用の記事タイトル対応表を使う場合でも、未登録slugを消さずslugへフォールバックする。
- 管理画面に `voter_key` を通常表示しない。

## 新規記事へ流用するときの必須チェック
1. 評価カードが記事末尾の標準位置にある。
2. `article_slug` がその記事固有値になっている。
3. 第1回記事のslugをコピーしたままになっていない。
4. backend側でそのslugを受け付けられる。
5. `article-feedback.js` が1回だけ読み込まれている。
6. `site-search.js` 等に古い投票処理が重複していない。
7. 1回目の投票が成功する。
8. 2回目は追加・上書きされず `投票済み` になる。
9. 投票済みの両ボタンが無効化され、待機カーソルが出ない。
10. `/admin/` で正しい記事slug / 記事名に1票だけ集計される。
11. JS更新時はキャッシュキーを更新する。

## 既存記事へ追加するとき
- 本文内容の意味変更とは分離して実施してよいが、記事HTMLの構造を壊さない。
- 記事ごとに投票コードをコピーして増殖させず、共通JSを使う。
- 既存のCSS・関連記事・フッター等を評価カード追加のために不要に作り替えない。
- 追加後は実際の本番または承認済みPreviewで、投票 → 管理ダッシュボード集計までE2E確認する。

## 完了条件
以下がすべて成立したとき、その記事への評価機能追加を完了とする。

- 記事固有slugで送信される。
- 1ブラウザ・1記事・1票がフロント / サーバー双方で守られる。
- 投票済みUIが直感的で、再送信されない。
- 管理ダッシュボードへ正しい記事単位で集計される。
- 個人情報やsecretを公開していない。
