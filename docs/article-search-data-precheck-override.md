# 記事制作・記事更新の検索データ事前確認オーバーライド

更新日: 2026-09-27
状態: **現行・正本追補**

## 位置づけ

この文書は、denkicontrol.com の**新規記事作成・既存記事更新・SEOメタ修正の前に行う検索データ確認**を定める。

記事制作・更新で検索データの扱いについて以下と矛盾した場合、本書を優先する。

- `docs/agent-runbook.md`
- `docs/article-workflow.md`
- `docs/new-article-checklist.md`
- `docs/legacy-article-refresh-template.md`

検索データの取得経路そのものは `docs/search-data-acquisition-rules.md` を正本とする。

標準データ経路:

`Google Search Console API / Bing Webmaster API -> GitHub Actions -> Supabase -> ChatGPT`

GSC Wizardや無料外部アプリを記事制作前チェックの標準ソースへ戻さない。

---

## 1. 適用対象

次の作業では、**本文やmetaを変更する前に検索データを確認することを必須**とする。

- 新規記事のテーマ・切り口決定
- 既存記事の本文改善
- title変更
- meta description変更
- H1 / H2 / H3 の変更
- 導入文・結論・FAQ・チェックリスト等の追加または再構成
- 関連記事・内部リンクの再設計
- 検索意図に合わせた記事リフレッシュ
- SEO目的を含む記事改善

### 例外

以下のような**検索意図や記事内容を変えない純粋な保守作業**は、この事前確認を省略してよい。

- CSSだけの表示崩れ修正
- 固定ヘッダーだけの統一
- 壊れた既存リンクの修正
- 誤字脱字のみの修正
- 画像パスだけの修正
- canonical等の明白な技術的誤りの修正

ただし、同じ作業で title / meta / 見出し / 本文も触る場合は省略しない。

---

## 2. 作業開始時の必須確認順

記事作成・更新を開始する時は、本文案を書く前に以下を行う。

1. GitHub main の最新記事・制作ルールを確認する。
2. `docs/search-data-acquisition-rules.md` を確認する。
3. Supabase の検索データが最新まで正常取得されているか確認する。
4. Google と Bing を**別々に**確認する。
5. 対象記事または対象テーマの検索実績を確認する。
6. 検索データから「検索者が何を知りたがっているか」「現在の記事で不足している説明は何か」を整理する。
7. その後にメーカー公式資料・一次情報を確認し、技術内容を確定する。
8. 検索需要と一次情報の両方を踏まえて title / meta / 見出し / 本文を設計する。

**検索データだけを見て技術内容を決めない。**
技術的事実・仕様・配線・設定・安全上の説明は、メーカー公式資料など一次情報を優先する。

---

## 3. 既存記事を更新する前に見るデータ

対象URLについて、可能な範囲で以下を確認する。

- 直近28日と前28日
- clicks
- impressions
- CTR
- average position / Bing側の対応指標
- 流入query
- 表示回数が多いquery
- 順位5〜15位付近のquery
- 表示回数が多いのにCTRが低いquery
- 直近で増えたquery / 減ったquery
- Googleでは強いがBingでは弱いquery、またはその逆

### 読み取り例

- **表示回数が多くCTRが低い**
  - title / meta description が検索意図に合っているか確認する。
  - ただしクリック狙いの誇張表現へ変えない。

- **順位5〜15位で表示回数が多い**
  - 本文の説明不足、見出し不足、比較不足、具体例不足、内部リンク不足を確認する。

- **関連queryが増えているが本文に説明がない**
  - 記事テーマと自然に一致する場合だけ、H2/H3や本文補足の候補にする。

- **Google/Bingで傾向が違う**
  - 片方の数値をもう片方へ推測しない。
  - サービス別の実績として保持して判断する。

---

## 4. 新規記事を作る前に見るデータ

新規記事では対象URLがまだ存在しないため、サイト全体のqueryデータから以下を確認する。

- 既存記事で拾えている関連query
- 既存記事が順位5〜15位で拾っている周辺query
- 表示回数が増えている関連テーマ
- 複数記事に分散している同系統query
- 既存記事では検索意図を十分に満たせていないquery
- Google/Bing双方で需要が確認できるテーマ

検索量だけを理由に記事を作らない。
既存記事との重複、サイトの学習導線、技術的な重要度、一次情報の有無も合わせて判断する。

---

## 5. 既存記事の改善候補・優先順位の決め方

既存記事の改善候補は、**過去に作成した固定バックログの並び順では決めない。**

毎回、作業開始時点の最新検索データを使ってサイト内の既存記事を再評価する。
`docs/existing-article-improvement-backlog.md` は改善履歴・完了状態・未完了候補の記録として使い、固定の優先順位表として使わない。

優先候補の判断材料:

- impressions が多い
- CTR が相対的に低い
- average position が5〜15位付近で伸びしろがある
- clicks / impressions / CTR / position が直近で悪化または改善している
- 検索queryが増えている、または検索意図が変化している
- GoogleとBingで差が大きい
- 画像・title・meta・本文・内部リンクに明確な改善余地がある
- メーカー公式資料・一次情報の更新がある

### 期間比較の注意

- 曜日差を考慮する。
- 日本の祝日・連休をまたぐ期間は、単純な前期間比較だけで異常と判断しない。
- 日曜日や長期休暇で検索需要が落ちる傾向が確認できる場合は、同曜日比較や複数週比較も使う。
- 一時的な需要減と、検索順位・CTR・コンテンツ品質の問題を分けて判断する。

### 完了済み記事の扱い

完成・凍結済み記事は原則として不用意に再編集しない。
ただし、以下のいずれかが確認できる場合は再評価候補へ戻してよい。

- 技術情報の更新
- 明確な不具合
- 検索データ上の大きな悪化
- 高い表示回数に対してCTRが継続的に低く、大きな改善余地がある
- 画像・title・meta・本文が現行ルールや現在の品質基準から大きく外れている

## 6. title / meta description への反映ルール

検索データは title / meta description を作る**参考根拠**として使う。

### title

- 実際に検索されている自然な用語を優先候補にする。
- 記事の主題と検索意図が一致する語だけ使う。
- 検索語を羅列しない。
- 同義語を不自然に全部詰め込まない。
- 技術的に不正確な検索語へ公式用語を合わせない。

### meta description

- 表示回数の多い検索意図に対して「この記事で何が分かるか」を自然に説明する。
- 記事本文にない内容を約束しない。
- CTR改善だけを目的に煽らない。
- キーワード列挙にしない。
- 既存のmeta文字数・表現ルールも維持する。

---

## 7. 見出し・本文への反映ルール

検索queryをそのまま見出しへ貼り付けるのではなく、**検索意図を抽象化して必要な説明へ変換**する。

反映候補:

- 読者が最初に知りたい結論
- 用語の違い
- 選び方・使い分け
- よく混同される点
- 動作原理
- 実務で見るポイント
- トラブル時の確認観点
- 関連する前提知識
- 次に読むべき関連記事

禁止:

- SEO目的だけの文章追加
- 同じ語の不自然な繰り返し
- 検索queryを大量に見出しへ並べる
- 検索需要を理由に技術的に誤った説明を採用する
- メーカー公式資料と矛盾する説明を検索語に合わせて残す

---

## 8. 検索データと一次情報の優先順位

役割を分ける。

### 検索データ

使う目的:

- 読者需要の把握
- 検索意図の把握
- 不足説明の発見
- title / metaの改善候補
- 内部リンク候補
- 更新優先度の判断

### メーカー公式資料・一次情報

使う目的:

- 技術的事実の確定
- 型式・仕様・配線・設定の確認
- 安全上の注意
- 正式用語・表記の確定

**需要は検索データ、正しさは一次情報**という役割分担を維持する。

---

## 9. データが古い・欠けている場合

- `search_collection_health` や最新取得日を確認する。
- 取得失敗期間を推測で補わない。
- Googleだけ取れている場合、Bingの数値をGoogleから作らない。逆も同様。
- データが古い場合は「検索データ未確認」または「最新データ不足」と明記して作業する。
- データ不足を理由にGSC Wizardへ自動フォールバックしない。
- 過去の固定バックログだけを根拠に更新対象を決めない。

---

## 10. 作業ログ / PRへの記録

本文やmetaを検索データを根拠に変更した場合、PRまたは作業ログに最低限以下を残す。

- 確認した期間（例: 直近28日 vs 前28日）
- Google / Bing のどちらを確認したか
- 変更判断に使った主要queryまたは傾向
- そのデータを受けて何を変更したか

全queryや大量の生データをPR本文へ貼る必要はない。
秘密情報・APIキー・tokenは絶対に記載しない。

---

## 11. 新しいチャット / 新しい担当での開始ルール

新規記事または既存記事改善を開始するチャット・担当は、本文案を作る前に本書を確認する。

標準開始順:

1. `docs/ai-governance.md`
2. `docs/ai-editorial-master-rules.md`
3. `docs/article-workflow.md`
4. `docs/new-article-checklist.md`
5. **`docs/article-search-data-precheck-override.md`**
6. `docs/search-data-acquisition-rules.md`
7. 記事タイプ別ルール / メーカー公式資料

既存記事リフレッシュでは `docs/legacy-article-refresh-template.md` も確認する。

短い依頼（例:「この記事直して」「次の記事進めて」「meta見直して」）でも、検索意図・本文・metaに触れる作業ならこの事前確認を省略しない。

---

## 12. 完了判定

記事制作・更新で検索データ確認が必要な作業は、以下を満たして初めて事前調査完了とする。

- Supabaseの最新取得状態を確認した
- Google/Bingを必要な範囲で確認した
- 対象URLまたは関連テーマのqueryを確認した
- 検索意図を整理した
- 一次情報を確認した
- title / meta / 見出し / 本文の変更理由を説明できる
- 検索語の詰め込みになっていない

この確認前に、検索需要を推測だけで決め打ちして本文・metaを完成させない。
