# 記事更新日・公式資料確認日ガード（正本追補）

更新日: 2026-09-17
状態: **現行・正本追補**

## 目的

既存記事の改善候補を検索データだけで選び、直近で改善・公開した記事を短期間に再編集してしまう事故を防ぐ。
また、記事内容を最後に更新した時期と、メーカー公式資料を最後に確認した時期を区別して記録・判断できるようにする。

## 適用範囲

- 新規記事作成
- 既存記事の本文改善
- title / meta description / H1 / H2 / H3 など検索意図に影響する変更
- 技術内容、仕様、配線、設定、安全上の説明の更新
- 既存記事改善候補の選定
- メーカー公式資料を根拠にする記事

CSSだけの修正、明白なリンク切れ修正、誤字脱字、画像形式変換など、記事の検索意図・技術内容を変えない保守作業は「内容更新日」を更新しなくてよい。

## 1. 2種類の日付を混同しない

記事では次の2種類の日付を別物として扱う。

### A. 記事内容の最終更新日

本文、title、meta description、主要見出し、技術説明など、読者が受け取る内容を実質的に変更した日。

### B. メーカー公式資料の最終確認日

記事の技術的根拠として使用するメーカー公式サイト、公式マニュアル、公式カタログ、公式FAQ、規格案内などを確認し、記事内容へ反映または再確認した日。

記事内容を編集していなくても、公式資料を再確認した場合はBだけ更新してよい。
逆に、読みやすさだけを改善して公式資料を再確認していない場合はAだけ更新し、Bを勝手に現在日にしない。

## 2. 記録場所

### メーカー公式資料を参照する記事

`docs/reference-notes/{slug}.md` を必須の制作・監査ログとして作成または更新し、最低限次を記録する。既存ファイルがある場合はそのファイルを継続利用する。

- メーカー名
- 公式URL
- 公式マニュアル名 / 公式資料名
- 確認日 `YYYY-MM-DD`
- 記事で使用した範囲
- 断定しない範囲

`docs/reference-notes/README.md` の既存テンプレートを維持する。記事HTMLに公式資料参照を表示しているのに対応する reference-notes が存在しない場合は、公開・完成判定前に補完する。

記事HTML内に「参考にした公式資料」「メーカー公式資料を確認して作成しています」等の表示を置く記事では、読者が資料の鮮度を判断できるよう、原則として **公式資料確認日** も表示する。

表示例:

```html
<p class="source-checked-date">公式資料確認日：2026-09-17</p>
```

既存記事へ日付を追加するためだけに一括改稿はしない。次回その記事を内容更新する時に追加・整合する。

### 記事内容の最終更新日

新規記事公開時または実質的な内容更新時は、記事HTML内に機械可読かつ人間にも確認できる形で最終内容更新日を残すことを標準とする。

推奨表示:

```html
<p class="article-updated">最終内容更新：<time datetime="2026-09-17">2026年9月17日</time></p>
```

既存記事に別の更新日表示方式がある場合は、その記事のテンプレートとの整合を優先し、同じ記事に重複した更新日表示を作らない。

## 3. 改善候補を選ぶ前の必須確認順

既存記事を「伸びていない」「CTRが低い」「順位が停滞している」等の理由で改善候補にする前に、必ず次の順で確認する。

1. `docs/existing-article-improvement-backlog.md` で完成・凍結 `[x]` か確認する。
2. 記事HTMLの最終内容更新日を確認する。
3. `docs/reference-notes/{slug}.md` と記事内の公式資料確認日を確認する。
4. GitHub履歴 / PR履歴で直近の実質的な内容更新がないか補完確認する。
5. その後にSupabaseのGoogle Search Console / Bing Webmaster実データを確認する。
6. 検索データと更新からの経過期間を合わせて改善要否を判断する。

日付表示が未導入の古い記事では、日付がないことを「長期間更新されていない」と決めつけず、GitHub履歴・改善バックログ・PR履歴を確認する。

## 4. 再編集クールダウン

本文、title、meta description、主要見出しなどを実質的に改善した記事は、原則として **最終内容更新から28日間は再改善候補から除外**する。

この28日間はGoogle/Bingの推移を観察する期間とする。

ただし次の場合は28日以内でも修正してよい。

- 明確な技術的誤り
- 安全上の問題
- メーカー公式資料の重要な更新
- リンク切れや表示崩れなど明確な不具合
- canonical / robots / 構造化データ等の重大な技術SEO不具合
- ユーザーが明示的に再修正を指示した場合

CTRや順位が数日悪化しただけでは例外にしない。

## 5. 完成・凍結済み記事の扱い

`docs/existing-article-improvement-backlog.md` で `[x]` の記事は、既存ルールどおり完成・凍結として扱う。

次のいずれかがない限り、検索データだけを理由に短期間で再編集しない。

- 28日以上経過後も検索データ上の大きな問題が継続
- 技術情報の更新
- 明確な不具合
- 検索意図との重大なずれが十分なデータで確認できた

## 6. 検索データとの組み合わせ

`docs/article-search-data-precheck-override.md` の検索データ事前確認は、この日付ガードを通過した記事に対して行う。

改善候補選定の原則:

`完成・凍結状態 → 最終内容更新日 → 公式資料確認日 → GitHub/PR履歴 → Google/Bing実データ`

検索データだけで改善対象を決めない。

## 7. PR / 作業ログ

記事の実質的な内容更新を行ったPRまたは作業ログには、可能な範囲で次を残す。

- 対象記事
- 最終内容更新日
- 公式資料を確認した場合は公式資料確認日
- 検索データを確認した場合は対象期間
- 再編集クールダウン対象か
- 改善理由

これにより、別チャットでも「最近触った記事かどうか」をGitHubだけで判断できる状態を維持する。

## 8. 禁止事項

- GitHubのファイル更新日時だけを記事内容の最終更新日として扱わない。
- CSS・画像圧縮・リンク修正だけで最終内容更新日を新しくしない。
- 公式資料を再確認していないのに公式資料確認日を現在日に更新しない。
- 日付が不明な古い記事へ推測の日付を入れない。
- 直近28日以内に改善した記事を、短期的なCTR・順位変動だけで再改稿しない。
- `[x]` 完成・凍結記事を検索数字だけで自動的に再編集しない。
