# 電気コントロール 設備管理Webアプリ 専用ルール v0.1

## 1. 位置づけ
本ルールは「電気コントロール 設備管理Webアプリ」の設計・実装・改修・運用に適用する専用ルールの叩き台である。
初期段階では一般公開せず、非公開環境で開発・検証する。今後の実装・検証・管理者判断に応じて本ルールを更新する。

主目的は次のとおり。
- 設備情報の管理
- PLC・HMI・サーボ・インバータ等の機器管理
- ソフトウェア／ファームウェアのバージョン管理
- バッテリー交換・点検時期の管理
- 個別通知
- AIによる写真入力補助
- 法人・組織単位の設備管理
- データ出力・バックアップ

## 2. 電気コントロール本体との導線
設備管理Webアプリは本体サイトと分離して設計してよいが、利用者の導線は分断しない。
- 電気コントロール本体 → ログイン／マイページ
- マイページ → 電気コントロールへ戻る
の双方向導線を必須とする。
ログイン後の固定ヘッダー等には、本体サイトへ戻る導線を常設する。

## 3. マイページの基本方式
ユーザーごとのHTMLページを個別生成しない。
共通マイページを使用し、ログイン中のユーザーID・法人ID・権限に応じて表示データを切り替える。

想定する主要画面:
- ダッシュボード
- 設備一覧
- 設備詳細
- 機器情報
- ソフト／バージョン情報
- バッテリー交換・点検履歴
- 通知予定
- メンバー管理
- データ出力
- アカウント設定

## 4. 法人・組織構造
個人利用だけを前提にせず、最初から法人・組織単位で管理できるデータ構造とする。
基本階層は次を想定する。

法人 → 工場／事業所 → 部門／ライン → 設備 → PLC・HMI・サーボ・インバータ等の機器

権限は最低限、次の階層を想定する。
- 法人管理者
- 管理者／責任者
- 一般ユーザー／現場担当者

将来の権限追加・細分化が可能な構造とする。

## 5. 権限・データ分離
画面上で項目を非表示にするだけではアクセス制御としない。
すべてのデータ取得・変更時にバックエンド側で次を検証する。
- ログインユーザー
- 法人ID
- 設備ID
- 所有・所属関係
- ユーザー権限

URL、APIパラメータ、設備ID等を書き換えても、他法人・他ユーザーの情報を取得・変更できないようにする。
ユーザー間・法人間のデータ分離を最重要要件とする。

## 6. 法人管理者機能
上位権限ユーザーは、自組織内について次を管理できるようにする。
- メンバー追加・無効化
- 権限変更
- この端末／全端末のログアウト
- 管理者による強制ログアウト
- 組織設定
- 通知設定
- 自動強制ログアウト時刻
- 操作履歴確認

一般ユーザーが法人全体のセキュリティ設定を変更できないようにする。

## 7. ログイン・セッション管理
次を実装可能な構造とする。
- この端末からログアウト
- 全端末からログアウト
- 管理者によるユーザー強制ログアウト
- パスワード変更時のセッション無効化
- 不審なログイン時のセッション無効化

法人ごとに、20:00、22:00、24:00等の指定時刻で自動強制ログアウトを設定できるようにする。
将来は平日のみ・曜日別・部門別・ユーザー別例外へ拡張可能な構造とする。
強制ログアウト前は警告を表示し、入力中データを可能な限り保護する。

## 8. UI・レスポンシブ方針
PC・タブレット・スマートフォンを単純な縮小表示にはしない。

### PC
既存の運営ダッシュボードに近い、一覧・詳細・管理をしやすいダッシュボード型UIを基本とする。

### タブレット
現場利用を重視する。
横向きは一覧＋詳細の2ペイン表示を積極的に使用し、縦向きはカード中心とする。
タッチ操作しやすいサイズを確保する。

### スマートフォン
アプリに近い直感操作を優先する。
- 大きなタップ領域
- カード型UI
- 主要機能への短い導線
- 必要最小限の入力
- 下部ナビゲーション等を必要に応じて採用

## 9. PWA・通知
最初からPWA化を考慮して設計する。
将来的に次を可能にする。
- ホーム画面追加
- ユーザー単位の個別Push通知
- バッテリー交換通知
- 点検期限通知
- ソフト／ファームウェア更新通知

通知先はユーザー単位・設備単位・法人単位で管理できる構造とする。

## 10. 設備管理データ
設備ごとに、少なくとも次の情報を登録可能な設計を想定する。
- 設備名
- 管理番号
- 工場／ライン
- メーカー
- PLC
- HMI
- サーボ
- インバータ
- ソフトウェア／ファームウェア
- 現在バージョン
- バッテリー情報
- 最終交換日
- 次回確認・交換予定日
- メモ

項目は固定しすぎず、将来追加可能な構造とする。

## 11. AI写真解析
写真は保管資産とせず、入力補助として扱うことを基本とする。

撮影 → AI解析 → 型式・日付・バージョン等を候補抽出 → ユーザー確認 → 文字情報のみ保存 → 画像破棄

AI解析結果を自動確定しない。
型式・製造番号・バージョン・日付・バッテリー交換情報等は誤認識を前提とし、利用者の確認・修正後に正式登録する。

## 12. データ保存
設備管理データと公開サイトデータを分離する。
顧客・ユーザー設備情報をGitHub、公開HTML、公開JSON等へ保存しない。
設備情報は認証済みバックエンドを経由してのみアクセスする。

## 13. 運営者アクセス
初期導入・開発・検証期間は、運営者本人が実データを確認できる構造を認める。
正式運用後は「通常時はユーザー設備詳細を閲覧しない」を原則とする。

障害対応、UI不具合、データ不整合、ユーザーからのサポート依頼、重大なバージョンアップ確認等、正当な理由がある場合のみ必要最小限アクセスする。

将来的には、
ユーザーがサポートアクセスを許可 → 一定時間だけ運営者アクセス可能 → 期限後に自動無効化
を目標とする。

## 14. 監査ログ
重要操作は監査ログへ残す。
最低限の対象:
- ログイン
- 強制ログアウト
- 権限変更
- ユーザー追加・削除・無効化
- 設備削除
- データ出力
- 運営者によるサポートアクセス
- 管理設定変更

誰が・いつ・何を・どの対象へ実行したか追跡可能にする。

## 15. プライバシー・データ利用
利用者へ実際の仕様に沿って明確に説明する。
基本方針:
- 登録設備情報を広告目的に利用しない
- 登録設備情報を販売しない
- 原則として第三者へ提供しない
- AI解析用写真は長期保存しない
- 必要以上の個人情報を収集しない
- 運営者アクセスは必要最小限とする
- データ利用目的を明示する

実装上アクセス可能であるにもかかわらず「運営者も絶対にアクセスできない」等の表現を使用しない。

## 16. データ出力・持ち出し
ユーザーが登録した情報をサービス内へ囲い込まない。
通常利用時・退会時ともに、可能な範囲でCSV・Excel・PDF等へ出力できる設計とする。
設備情報・機器情報・履歴等を一括エクスポートできるようにする。

## 17. 削除・退会
退会時は、データ出力 → 削除対象確認 → 必要な法人管理者確認 → データ削除、の安全な流れを設ける。
一般ユーザーの退会によって法人所有の設備データが削除されないようにする。
法人利用時の設備データ所有主体は法人側を基本とする。

## 18. 初期開発フェーズ
最初から全機能を実装しない。

### Phase 1
- ログイン
- マイページ
- 設備登録
- 設備一覧・詳細
- PLC／サーボ等の基本情報
- バージョン管理
- バッテリー交換履歴
- PC／タブレット／スマホUI

### Phase 2
- 法人管理
- メンバー・権限管理
- 通知
- 強制ログアウト設定
- データ出力

### Phase 3
- PWA
- Push通知
- AI写真解析
- メーカー最新バージョン照合
- 高度な分析

フェーズ順は固定ではなく、管理者の明示指示により変更できる。

## 19. 公開条件
開発段階では非公開とする。
正式公開前に最低限、次を確認する。
- 認証
- ユーザー間・法人間データ分離
- 権限管理
- バックアップ
- 監査ログ
- プライバシー表示
- 退会・データ出力
- PC・タブレット・スマホ動作

「画面が完成した」だけでは公開条件を満たさない。

## 20. 最重要原則
本アプリは次を両立する。
1. ユーザー・法人間のデータ分離を最優先する
2. 現場担当者には簡単に使える
3. 管理者には組織全体を管理しやすい
4. 運営者にはサービス利用状況を分析しやすい
5. 利用者自身がデータを持ち出せる

本ルールはv0.1の叩き台であり、実装を進めながら管理者判断を随時追記・更新する。

## 21. グローバル展開方針
本アプリは日本国内専用サービスとして設計しない。
初期段階から日本国内と海外市場を同時に視野へ入れ、将来の多言語・多地域展開を阻害しない構造とする。

基本方針:
- 日本語だけを前提としたデータ構造・UI実装にしない
- 英語対応を初期段階から想定し、UI文言を直接ハードコードしすぎない
- 将来は多言語追加が可能な国際化（i18n）構造とする
- 日付・時刻・タイムゾーンを地域ごとに扱えるようにする
- SI単位を基本としつつ、psi・inch・°F等の地域単位表示へ拡張可能にする
- メーカー・型式データは日本メーカーに限定せず、海外メーカーも登録・検索・照合可能な構造とする
- PLC、サーボ、インバータ、HMI等の分類は特定国内メーカー依存にしない
- 法人 → 拠点／工場 → 部門／ライン → 設備 → 機器、という階層は国・地域に依存しない構造とする
- 通知・カレンダー・期限判定はユーザーまたは法人のタイムゾーンを基準に扱う
- 住所・電話番号・会社情報など、地域ごとに形式が異なる項目は固定書式へ過度に依存しない
- 決済・税・利用規約・プライバシー要件は国や地域で異なるため、海外公開時には対象地域ごとに別途確認する

開発・市場展開は「国内完成後に海外対応」ではなく、
**国内版とグローバル版を同一基盤で同時進行できる設計**
を原則とする。

初期の実利用・検証は日本語中心でもよいが、それを理由に海外展開を困難にする実装を採用しない。
