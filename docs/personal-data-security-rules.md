# 電気コントロール 個人情報・機密情報保護運用ルール

制定: 2026-10-16
適用: denkicontrol.com / Syasu-pixel/my-site に関係する相談フォーム、案件管理、管理画面、外部連携、Preview、AI作業
状態: 運用提案（Draft PRでレビュー後に正本化）

## 1. 上位原則
- 収集する個人情報・企業機密はサービス提供に必要な最小限にする。
- 氏名、返信用メールアドレス、相談本文、設備図面・PLCプロジェクト、見積書、添付資料、IPアドレス等は、組み合わせにより識別・機密性が生じるものを含め取り扱いを評価する。
- 機密の保護は「暗号化済み」だけで完結しない。復号鍵、管理権限、保存先、通知先、バックアップを含めて保護する。
- 個人情報を含む実データを公開リポジトリ、PR、Issue、サンプル、CIログ、公開Preview、外部AIのプロンプトに投入しない。
- 最終公開・HIGHリスク変更には人間の承認を必要とする。既存のPreviewとProductionを分離する。
- 関連規程: `docs/ai-governance.md` の高リスク分類と承認規則を継承する。

## 2. データ台帳（収集開始前の確認）
各機能で最低限、以下を台帳化する。
- 収集項目、利用目的、法的根拠・本人への説明、必須/任意、公開範囲
- 収集元・保存先（D1 / メール / Google Sheets / 外部サービス等）、連携・委託先
- アクセスできる役割、保持期間と削除条件、バックアップの扱い
- 暗号化の範囲、鍵の保管場所、インシデント対応担当・連絡経路
- 事前に決められない保持期間・削除条件は「未決」として機能公開前に責任者が決定する。推測で期間を記載しない。

## 3. 相談フォームと顧客資料
- 返信のための情報と案件遂行に必要な資料以外は原則取得しない。不要な住所・電話番号・資格情報を必須化しない。
- パスワード付きZIPと別送パスワードの仕組みは維持しつつ、**パスワードと暗号化ファイルを同じ管理境界から一括取得できないか**を監査する。別フォームであっても保存先・管理権限が共通なら独立とはみなさない。
- 本番フォームのテストに実顧客の個人情報、図面、認証情報を使わない。
- 添付ファイルの型・容量・アクセス権・ダウンロード期限・マルウェア対策を別途点検する。
- メール通知には必要最小限のみ載せる。添付資料・パスワード・全文の転記は原則避け、認証済みの管理画面から確認する設計を優先する。

## 4. 認証・権限・Secrets
- 管理画面、API、D1/DB、資料ダウンロードの全経路でサーバー側の認証と権限検証を行う。URLが推測困難なだけでは保護とみなさない。
- Cloudflare Secrets / GitHub Actions Secrets等の専用保管を使い、ソース、クライアントJS、PR本文、ログに認証情報を埋め込まない。
- Secretsは環境別・機能別に最小権限化し、利用する暗号鍵の保管・復号権限を分離する。鍵の同一侵害境界内での露出を検討する。
- 認証情報漏洩のおそれが判明したら対象を無効化・再発行し、関係する連携先と通知先も点検する。
- 管理者アカウントへの多要素認証を基本とする。

## 5. ログと自動監視
- 認証失敗急増、権限外アクセス、大量ダウンロード、不審なAPIアクセス、Secrets変更、権限変更、想定外の公開URLを検知候補とする。
- ログには相談本文、トークン、添付資料、パスワード、フルURL内の秘密情報を残さない。必要な識別子は最小化する。
- 監視ルールはまず観測・警告から導入し、誤検知と既存運用への影響を確認してから自動遮断等を検討する。

## 6. Preview / 外部連携 / AI
- Preview URLはアクセス制御と有効期限・無効化手段を検討する。noindex単体はアクセス制御ではない。
- Previewで実顧客データや本番Secretsを使わず、本番への送信・通知を分離する。
- Google Sheets、メール、Webhook、Cloudflare、GitHubその他の外部連携は権限、保存範囲、停止・トークン失効手順を台帳に記録する。
- AIレビューでは匿名化・ダミーデータを原則とし、顧客機密の外部送信には目的、委託先条件、承認を要する。

## 7. 不正アクセス・流出疑い発生時
1. アラート、報告、発見日時を記録し、事実と推測を区別する。
2. 被害拡大を抑えるため、アクセス遮断、該当権限・キーの一時停止などを検討する。
3. ログ・構成・関連記録を改ざんせず保全し、影響した期間、データ種別、対象者、外部連携を調査する。
4. 同一侵害範囲のSecrets、暗号鍵、Webhook URL、共有Preview URL等を失効・切替し、二次被害を確認する。
5. 日本の個人情報保護法等に基づく報告・本人通知の要否と期限を確認し、必要な手続きを行う。国外利用者・委託先の法域にも留意する。
6. 影響を受けた方へ、確認できた事実、リスク、必要な対応、問い合わせ先を適切に案内し、未確定事項は未確定と明記する。
7. 原因・再発防止策・変更履歴を残し、復旧後にレビューする。

## 8. 定期点検と変更ゲート
- 新規フォーム、添付、外部連携、会員登録、案件管理機能を公開する前に本ルールのチェックを必須にする。
- 定期点検: データ台帳、アクセス権、古い共有URL、Secrets、保持期限、削除処理、監視ルール。
- 実装や公開ポリシー改訂は別PRで差分とリスクを検証し、人間確認後にmainへ反映する。
- この文書の追加だけで設定変更・監視稼働・漏洩調査が完了したものとはみなさない。
