# PLCラダー編集・作成ルール

この文書は、既設設備のPLCラダーをChatGPT / Codexで確認・整理・再作成するときの共通ルールです。

## 1. 最優先は「現状動作を壊さない」

- 稼働中設備では、見た目をきれいにするためだけにロジックを変更しない。
- 既存MAIN、コメント、PDF、現地写真を先に照合する。
- 既存回路から削除する場合は、後半や旧回路に現在も必要な出力・リセット・補助回路が残っていないか必ず確認する。
- 用途が断定できないI/Oは削除せず、`現地確認必須` として残す。
- コメントが無いことを「未使用」と判断しない。

## 2. 共通条件は枝分かれを優先する

同じ条件から複数の出力・内部リレーを動かす場合は、可能な限り共通条件を1回だけ書き、その後で枝分かれさせる。

例：

```text
        ┌→ Y005
X004 ───┤
        └→ Y006
```

以下のように同じ条件を重複して書くより、上記を優先する。

```text
LD X004
OUT Y005

LD X004
OUT Y006
```

目的は次の3点。

- ラダーを見た瞬間に「同じ条件で同時に動く」ことが分かる
- 同じ接点条件の重複を減らす
- PLCの使用ステップ数を抑える

## 3. 長い共通条件ほどMPS / MRD / MPPを活用する

三菱FX系で、複数枝が同じ長い条件を共有する場合は、MPS / MRD / MPPによる分岐を積極的に検討する。

例：

```text
共通条件 → MPS
         ├→ X005 → M100
         ├→ X006 → M101
         ├→ X007 → M102
         └→ X025 → M103
```

各枝ごとに共通条件を全部書き直す方式より、可読性とステップ節約の両方を優先する。

ただし、短い条件で無理にMPS / MRD / MPPを使い、かえって読みにくくなる場合は使用しない。

## 4. GPTが新規にラダーを書く場合の優先順位

次の順番で評価する。

1. 正しい動作
2. 既設設備との整合性
3. 安全側の停止・復帰条件
4. 読みやすさ
5. 共通条件の整理
6. 使用ステップ数の節約

「動くからOK」ではなく、現場で後から読む人が追いやすい回路を作る。

## 5. 役割ごとにTitleを付ける

GX Works2の`[Title]`を使い、回路を機能単位で区切る。

例：

- `[Title]Aライン 手動運転`
- `[Title]Aライン 自動運転`
- `[Title]CV運転出力（手動 OR 自動）`
- `[Title]センサー監視タイマ`
- `[Title]運転表示`
- `[Title]異常保持・異常表示`
- `[Title]インバータリセット`
- `[Title]現地確認必須：Y011`

Titleは長くしすぎず、ページを見た瞬間に回路の役割が分かる名前にする。

## 6. デバイスコメントは「物理用途」が分かる名前にする

単に「遅延出力」「信号」だけで終わらせず、分かる範囲で物理用途まで書く。

例：

- `Y005 = INV1-3 リセット`
- `Y006 = INV4 リセット`
- `Y024 = 盤面CNT1カウント信号`
- `T1 = 満タン検出遅延`

用途が不明な場合は推測せず、短く`現地確認必須`を付ける。

## 7. 元ラダーとの比較を必ず行う

整理版を作る前後で、少なくとも以下を比較する。

- X入力の使用先
- Y出力の使用先
- M内部リレー
- Tタイマ
- Cカウンタ
- SET / RST
- M8000 / M8001 / M8013など特殊リレー
- 後半に残っている独立回路

特に、古い回路をM8001等で無効化している場合でも、その中に現在必要な独立出力が残っていないか確認する。

## 8. 現地で確認できた内容はコメントへ反映する

現地で用途が判明したら、仮コメントをそのままにしない。

例：

- `Y024 現地確認` → `Y024 盤面CNT1カウント信号`
- `Y006 INV4-6リセット` → 現設備がINV1～4のみなら `Y006 INV4 リセット`

ラダー本体とコメントの意味が食い違わない状態を保つ。

## 9. GX Works2向けCSV出力ルール

GX Works2用にMAINを出力するときは、既存プロジェクトで確認済みの形式を優先する。

- UTF-16 LE / BOM
- タブ区切り
- CRLF
- 7列形式
- `[Title]`は行間ステートメントへ入れる
- FX3G / FX3GCでは、他シリーズ用の命令や書式をそのまま流用しない

コメントCSVは、GX Works2の文字数制限を考慮し、短く実用的な文言にする。

## 10. このルールの基本思想

ラダーは、単に命令数を減らせば良いわけではない。

**「動作が正しい」「現場で読める」「共通条件が分かる」「余計なステップを使わない」**

この4点を同時に満たすことを目標とする。

特にChatGPT / Codexが回路を提案するときは、同じ条件を何度も書く前に、枝分かれでまとめられないかを必ず検討する。

## 11. 起動成立シーケンスを削除前に確認する

既設ラダーを整理・再作成するときは、通常運転中だけでなく、**電源投入時・停止復帰時・異常復帰時だけ働く回路**を必ず確認する。

特に、外部機器に対して次のような成立順序がないかを確認する。

```text
出力要求
  ↓
外部機器が成立するまでの時間差
  ↓
フィードバック入力成立
  ↓
通常監視へ移行
```

確認対象の例：

- マグネットコンタクタ
- インバータ
- サーボ
- 外部電源・制御電源
- 電磁弁や空圧機器の成立確認
- 外部盤とのREADY / RUN / NORMAL信号
- 通信機器の起動完了信号

ここで重要なのは、**全設備へ一律に起動遅延タイマを追加することではない。**
既設設備が持つ「出力とフィードバックの成立順序」を確認し、その役割を理解してから整理する。

旧ラダーにタイマ・内部リレー・自己保持・補助接点がある場合は、単体で不要判定せず、関連するY出力・X入力・SET/RSTとひとまとまりで追う。

## 12. 安全系と一般機器の立上り監視を混同しない

一般機器の立上り待ち・フィードバック待ちと、非常停止等の安全系は別のものとして扱う。

- 安全系を「起動時だけ無視する」目的で遅延・マスクしない。
- 安全回路の成立を、一般機器の起動猶予タイマで代用しない。
- 安全入力と一般フィードバック入力の用途が不明な場合は、コメント名だけで断定しない。
- 実機変更前に図面・現物配線・既設ラダー・現地運用を照合する。

安全機能の変更や実機試運転は、設備の安全手順と権限を持つ担当者の確認を前提とする。

## 13. 旧回路削除時は「通常運転で使うか」だけで判断しない

削除候補回路は、次の状態でも使われていないか確認する。

- 電源投入直後
- 停止からの再始動
- 非常停止・異常からの復帰
- 外部機器の投入確認
- リセット時
- モード切替時
- 一定時間だけ成立する監視
- 異常発生時だけ使う出力・保持・解除

「通常運転中にONしていない」「コメントが無い」「古い番号に見える」だけでは撤去理由にしない。

未確定のI/Oや補助回路は、`現地確認必須` として保留し、案件固有ログへ確認事項を残す。

## 14. 案件固有ログと共通ルールを分離する

個別設備で起きた症状、I/O番号、現地配線、未確定事項は案件固有ログへ記録する。

共通ルール側には、複数設備で再利用できる判断基準だけを残す。

案件ログでは少なくとも次を区別する。

- 確認済みの事実
- 現地担当者から得た仕様
- 旧ラダー・図面から読み取った内容
- 推定
- 未確定事項
- 次回確認事項

推定を確定仕様として残さない。
