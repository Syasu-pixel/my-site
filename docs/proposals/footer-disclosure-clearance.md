# 固定「上に戻る」ボタンと広告開示の重なり：分離修正案

状態：設計Draft。未採用・未実装・未公開。記事刷新PRと混ぜず、mainへマージしない。

## 問題と根拠

2026-11-18、圧着記事 `articles/crimping-tips.html` の390px幅で、固定ボタンが広告開示文末を覆うことを変更前・変更後の原画で確認した。今回の記事刷新による新規回帰ではない。広告開示を削除・短縮・非表示にして解消してはならない。

基準mainは `d05ba287b0d273e89976638e651d56de55063b1f`。本番GETのfooter HTMLは診断beforeとbyte一致。原点復帰記事の文字輪郭差とは別問題として扱う。

診断記録は [PR #1983](https://github.com/Syasu-pixel/my-site/pull/1983)。これは未マージで終了した一時診断であり、今回の機能修正を承認した記録ではない。

## 正本と影響範囲

- 編集元は `.github/article-components/integration-compat.css` / `.github/article-components/integration-compat.js` を候補とする。`scripts/build-integrated-review.mjs` が生成資産へコピーする。生成済み `assets/css/article-integration-compat.css` を直接編集しない。
- footer HTML variantは `.github/site-shells/manifest.json` に登録される。今回の第一案ではvariant・記事本文・既存のボタンclick処理を変更しない。
- 固定baseを全記事検索した結果、`scrollTopBtn` を持つ記事は26件、ボタンのCSS宣言は1種類。日本語記事に限定されていた。ただし26件すべてで重なりを目視確認したという意味ではない。
- 共通compatを変更する実装PRは全記事へ配信されるため、条件に合う26件と非対象記事を区別した静的検証に加え、既存ルールどおり全記事の統合検査が必要。非記事の専用構造へ流用しない。

## 推奨する実装方針（検証後に採否判断）

狭幅で固定ボタンを残しつつ、footerの文字・リンクがボタンの水平領域へ入らない専用の空き領域を確保する案を第一候補とする。単にfooter下の余白を増すだけでは、スクロール途中に文字が固定ボタンの下を通る問題が残る。

1. 初期化は独立した処理にし、既存の検索・目次・lightboxの早期returnに依存させない。対象は単一の `footer.site-footer` と、直後の単一 `button#scrollTopBtn`。そのほかの構造は変更せず未対応として検出する。
2. ボタンの文面・アクセシビリティ名・click handler・上部への移動・表示開始条件を保持する。ボタンを単に消す、別の本文へ押し上げる、別ボタンを複製する方法を避ける。
3. 640px以下を最初の評価範囲とし、表示中の実測ボタン幅・右端からの距離・余裕を使ってfooter内の右側の空き領域を決める。ボタン幅を固定値と仮定しない。200%文字拡大でも開示文の上に重ならないことを必須とする。
4. フッターのHTML/text/href順を変えず、専用クラスと専用CSSカスタムプロパティだけで対象を限定する。元のpaddingを上書き破壊せず保持し、解除時に正確に戻す。左右反転・想定外の位置指定は未対応として検証で止める。
5. ボタンの初回表示・font ready・画面resize/向き変更を扱う。ResizeObserverはボタンを観測し、footer自身の変更で自己再計測を繰り返さない。requestAnimationFrameで集約し、同値のstyle再書込みをしない。ボタン非表示時に幅0から誤った余白を確定しない。
6. 可読性を損ねるほど列が狭くなる場合は、この方式を採用しない。可読性は横overflowゼロ・全文可視・リンクfocus/hit可用に加え、320px/200%の実画面で極端な1文字折返し等がないことを目視する。重なりゼロだけでは合格にしない。320px/200%で可読性を満たさない場合は、footer到達時に既存ボタンを明示的な非重複の操作行へ移す設計を別案として比較する。観測と再配置が循環する実装は不可。

これは方法の提案であり、CSS/JS実装と画面検査は未実施。640pxや余裕値は採用済み仕様として扱わない。641px/768px等で重なりが残れば対象外と片付けず、breakpointを再評価する。

## 採用しない近道

- 広告開示を削除、切詰め、透明化する。
- z-indexだけ変えて、文字かボタンのどちらかを操作不能にする。
- 既存記事のfooterへ個別の空白や改行を挿入して共通問題を隠す。
- 固定80px等の余白だけで、拡大・長文・スクロール途中の非重複を保証したとする。
- 既存画像のbaselineを候補へ置換し、画素閾値や契約検査を緩めて通す。

## 実装PRで必要な検査

1. **負の対照**：現行mainの圧着390pxは広告開示のtext Rangeとボタン矩形が交差し、検査が失敗すること。修正後は同条件で交差ゼロ。PNG目視だけでなくリンク文字・全開示文字のRangeを判定する。
2. **幅・状態**：320/390/640/641/768/1440、light/dark、通常/200%文字拡大、縦横切替、最下部とfooter進入中の複数スクロール位置、ボタン表示/非表示、再訪。
3. **操作**：Tab focusとfocus ring、Enter/Space/clickで上部へ移動、リンクhit test、既存のreduced-motion挙動、キーボード/タッチの操作を保持。実フォーム送信や広告clickはしない。
4. **範囲**：26件の対象inventory全件、ボタンなし記事、英語記事、専用記事、非記事ページに新規の空白・横スクロール・DOM変更がないこと。
5. **保全**：本文・画像・SEO・Amazonリンク・開示全文・停止中サービス・元click handler・既存投票JSを保持。生成candidateと正規publicationの一致を検証する。
6. **全件統合**：共通compat変更として既存の全記事/分割ブラウザ検査と集約を実行し、最終成果物のPC/スマホ明暗を目視する。意図したfooter変更と無関係な輪郭差を区別し、既存guardに専用例外や閾値変更を加えない。意図した変更もzero-diff検査で失敗し得るため、CI成功は事前に約束しない。失敗は個別の承認・根拠記録と既存の正規公開手順で扱い、必須checkを迂回しない。未承認候補へのbaseline付替えは禁止し、基準の昇格は最終Preview承認・本番配信確認後の既存手順に従う。
7. **失敗系**：ResizeObserver unavailable、想定外の重複ボタン、missing footer、遅いfont読み込み、ボタンtext変更でクラッシュ・ループ・開示消失を起こさないこと。未対応の場合は解消済みと報告しない。

## 記事公開と分離する手順

1. この設計Draftを独立レビューし、採用する方式と可読性の判断を確定する。
2. 最新mainから別の実装Draft PRを作り、圧着・原点復帰等の未公開本文や画像を取り込まない。
3. 元の本番基準を保存し、意図したfooter差分と元から存在する差を記録する。確認用資産をmainへ混ぜない。
4. 実装PRの正式CI・本人確認用Preview・独立レビュー完了後、共通機能の公開承認を別途受ける。記事公開承認をこの共通変更の承認へ拡張しない。
5. 通常マージとPages配信後に本番HTML/資産hash、対象390pxの広告開示と上へ戻る操作、非対象例を確認する。
6. rollbackはこの実装PRだけの通常revertで可能にする。記事本文のrevert、履歴書換え、権限変更をしない。
