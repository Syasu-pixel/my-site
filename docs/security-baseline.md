# Denkicontrol Security Baseline

## 1. 位置づけ

この文書は `Syasu-pixel/my-site` の全作業で開始時に読む必須セキュリティ正本とする。既存の `docs/ai-governance.md` にある秘密情報保護・最小権限、Preview隔離、各機能固有ルールを置き換えず、サイト・管理機能・API実装で守る最低基準を具体化する。

記事、画像、CSS等の通常作業でも最低限の禁止事項を確認する。管理画面、API、認証、DB、フォーム、メール送信、ファイル処理、外部サービス、Secrets、CI/CD、Preview、本番公開に触れる場合は該当する詳細確認まで行う。

## 2. 全作業で守る原則

- 既存の認証、認可、noindex、セキュリティヘッダー、入力検証、送信隔離、権限制限、Secrets管理を、目的と影響を確認せず削除・緩和しない。
- APIキー、アクセストークン、パスワード、Webhook secret、秘密鍵、DB接続情報、セッショントークン等をHTML、JavaScript、Markdown、PR本文、Decision Log、通常ログへ平文で保存しない。既存の `docs/ai-governance.md` 第14節を維持する。
- Agent、CI/CD、Worker、Edge Function、DB、外部サービスへ必要以上の権限を与えない。新規機能で既存の広権限secretを安易に共用しない。
- 管理画面やAPIのURLを知られないことを防御として扱わない。保護対象はサーバー側の認証・認可で守る。
- 存在しないURLは原則404/410を正しく返す。無関係なページへ一律リダイレクトして隠さない。
- 非表示ボタン、JavaScriptの画面制御、HTML属性、フロント側バリデーションだけで管理操作やデータ保護を成立させない。

## 3. 認証・認可

管理画面、管理API、DB更新、メール送信、公開処理、削除、設定変更、案件データ、非公開データ等を扱う場合は次を満たす。

- 認証が必要な操作はサーバー側でも認証を検証する。
- 権限が必要な操作は各リクエストでサーバー側認可を行う。
- 原則を default deny とし、許可条件を満たした場合だけアクセスを許可する。
- 未ログイン状態で保護対象の読み取り・更新・削除・送信が成功しないことを確認する。
- 対象ID等を扱う場合、対象ごとの操作権限を確認する。
- ログアウト、失効、期限切れ後のセッション・トークンを受理しない。
- 認証Cookieを自前で扱う場合は、用途に応じて `Secure`、`HttpOnly`、適切な `SameSite`、期限・失効を設計する。
- 管理権限を持つ外部サービスのアカウントでは、提供されている場合MFAを優先する。
- 新しい管理機能で既存の管理パスワードを安易に使い回さない。既存の共有認証を変更する場合は影響範囲を先に監査する。

## 4. API・フォーム・外部入力

- ブラウザ、外部サービス、Webhook、URLパラメータ、フォーム、JSON等、信頼境界の外から来る値は未信頼入力として扱う。
- サーバー側で型、長さ、範囲、形式、許容値、必須項目、必要に応じてrequest size / content typeを検証する。
- DB、HTML出力、メール、ファイル名、URL等、それぞれの出力先に適した安全なAPI・エンコードを使う。
- エラー応答へ内部パス、DB情報、secret、token、設定値等を不用意に含めない。
- 公開フォームや高コストAPI、メール送信、認証試行等では、影響に応じてレート制限、重複送信防止、idempotency等を検討する。
- CORSを必要以上に広げない。管理・非公開APIでは公開範囲と認証方式を確認する。

## 5. Secrets・CI/CD・外部サービス

- SecretsはGitHub Secrets、Cloudflare/Supabase等の適切な秘密管理機構または環境変数で扱い、クライアントへ配信されるコードに埋め込まない。
- 新しいsecretには用途と必要権限を限定し、可能なら機能・環境ごとに分離する。
- secretは失効・ローテーション可能な構成を優先する。漏えいが疑われる場合は当該secretを失効・再発行する。
- CI/CD、Preview、テスト出力、スクリーンショット、artifact、ログへsecretを出さない。
- Production権限を必要としないPreview・監査・記事制作へProduction secretを渡さない。
- 外部サービス追加時は、必要権限、保存データ、送信先、課金影響、失効方法、障害時の影響を確認する。

## 6. ログ・監視

- 認証失敗、認可拒否、重要な管理操作、入力検証失敗、設定変更、異常な大量リクエスト等は、リスクに応じて監査可能な形で記録する。
- パスワード、APIキー、アクセストークン、秘密鍵、完全なセッションID、DB接続情報等をログへ平文保存しない。
- ログは異常検知と原因調査に必要なイベントを選び、個人情報は必要性と保存範囲を確認する。
- 少数の404だけで重大事象と断定しない。短時間に異常なアクセスが継続する場合は監視・調査対象として扱う。

## 7. Preview・公開面

- Preview隔離の正本は既存の `docs/ai-governance.md` とPreview関連文書を維持する。
- Preview URLを本番sitemap、search-index、IndexNow等へ入れず、noindex等の現行隔離を維持する。
- PreviewのためにProduction上へ一時的な公開ファイル・秘密情報・管理用エンドポイントを作らない。
- 公開候補へ不要なdebug機能、テスト用の認証例外、仮credential、内部専用情報を残さない。
- セキュリティヘッダーを変更する場合は、CSP、frame制御、HTTPS関連、Referrer Policy等への影響を確認する。

## 8. 詳細チェックが必須になる変更

次を新設・変更・削除する作業では、通常の表示・機能確認に加えてセキュリティ確認を行う。

- ログイン、ログアウト、セッション、Cookie、認証、認可、管理者権限
- 管理画面、管理API、非公開データ、案件データ
- API、Worker、Edge Function、Webhook、DB/RPC、Storage
- フォーム、ファイルアップロード、メール送信、PDF生成・保存
- Secrets、環境変数、OAuth、外部サービス連携、CI/CD権限
- CSP/CORS/セキュリティヘッダー、Preview隔離、本番公開方式
- ユーザー投稿、個人情報、将来の会員・コミュニティ機能

最低確認項目:
1. 未認証状態で保護対象へアクセスできない。
2. 認証済みでも権限外の対象・操作を実行できない。
3. 認証・認可をサーバー側で確認している。
4. 外部入力のサーバー側検証がある。
5. secret / token / passwordがGit、HTML/JS、ログ、Preview、artifactへ露出しない。
6. 付与権限が必要最小限である。
7. エラー応答が内部情報を過剰に公開しない。
8. 高頻度・高コスト・送信系処理では悪用耐性を確認する。
9. 変更前に存在した防御を意図せず弱めていない。
10. 未確認項目がある場合は完了報告で明示し、根拠なく「安全」と断定しない。

## 9. 変更時の扱い

- セキュリティ基準を緩和する変更は通常の表示改善・記事更新の付随変更として行わない。理由、影響、代替策を明示し、管理者判断を必要とするHIGH変更として扱う。
- 既存機能の監査で問題を発見しても、依頼範囲外の大規模改修を同一PRへ混ぜない。重大な問題がある場合は安全側に倒して管理者へ報告する。
- 本書を追加しただけで既存システムが自動的に安全になったとは扱わない。AI編集部、運営ダッシュボード、オンライン相談等は必要に応じて別途現状監査する。

## 10. 参考基準

実装判断では現行のOWASP Cheat Sheet Series等のセキュリティガイダンスを参考にする。特にAuthorization、Authentication、Secrets Management、Input Validation、Logging、REST Security、Secure Code Reviewの考え方を基準とし、実作業時に現行資料を確認する。
