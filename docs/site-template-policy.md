# サイト共通ひな形・構造分離方針 v1（提案）

- 作成日: 2026-09-18
- 状態: PROPOSED / ルール案。ルール採用・実装開始・本番公開の承認を分離する。
- リポジトリ: `Syasu-pixel/my-site`
- 移行状況の正本: [site-template-migration-status.md](site-template-migration-status.md)
- 横断確認: [site-template-rule-audit.md](site-template-rule-audit.md)

## 1. 目的と適用範囲
見た目・URL・内容を維持し、共通の構造を一か所修正して利用ページへ反映できるようにする。記事作成ではタイトル・画像・本文など固有内容に集中でき、後からの編集を容易にする。速度向上は測定対象であり保証しない。

この方針はサイト構造の移行に限定したマスタールールの補足とする。安全・法令・秘密情報保護・管理者の権限は `ai-governance.md`、制作・公開の全体ルールは `ai-editorial-master-rules.md` が上位。本文・画像品質・検索・翻訳の各正本を置き換えない。

管理者が本方針を採用した後、台帳に移行済みと記録された既存ページと、利用可能なひな形・正本を確認して台帳へ新規登録するページでは、「完成記事HTMLの完全コピー」を「レイアウト＋共通部品＋記事固有データ」へ置き換える。利用可能なひな形がない新規ページと未移行ページは従来方式を維持する。初回移行PRに限る例外は第6節に定める。ルール案の追加自体は実装開始許可ではない。

## 2. 3層の分離
1. **共通部品**: 固定ヘッダー、検索欄、言語メニュー、フッター、応援カード、関連記事カード、記事評価カード等。各部品に正本を一つ定める。
2. **ページレイアウト**: ヘッダー・ヒーロー・本文・サイドバー・フッターの配置や必須／任意領域。用途ごとに組み合わせる。
3. **ページ固有データ／本文**: URL、slug、言語、タイトル、説明、画像、本文、カテゴリ、関連記事、シリーズ回数、実在する日英対応先等。

同じ部品をページごとに複製して修正しない。構造とCSS・動作も部品の責任範囲を定義し、HTMLだけ共通にして同じ修正を各記事のCSSへ要求する設計を最終形にしない。共通CSSとページ専用CSSの優先順位を明確にし、既存の表示差は勝手に均一化しない。

記事固有情報を共通部品へ固定しない。記事本文・会話・表・コード・図の順序を、移行の都合だけで変えない。初回から本文をJSONやMarkdownへ強制変換する必要はなく、既存HTML断片も選べる。管理しやすさと既存内容の保存を優先する。

## 3. ページ種別と例外
以下は設計上の区分で、実装名やファイル名の決定ではない。

| 種別 | 構造の扱い | 固有機能 |
|---|---|---|
| トップ | トップ専用レイアウト | 人気・新着・カテゴリ棚。通常記事へ合わせない |
| 通常記事 | 共通記事レイアウト | 基礎・比較・手順・トラブル等の内容タイプを保持 |
| キャリア・転職記事 | 通常記事を基本に必要な専用部品を追加 | 比較、広告表記、相談等の既存導線を保持 |
| ハブ・カテゴリ・一覧 | 一覧／ハブ用レイアウト | 分類、フィルタ、回遊導線を保持 |
| PLC設備設計シリーズ | 記事部品を共有するシリーズ用構成 | シリーズ目次、各回、前後回、図・表・資料の専用領域 |
| GX Works2等のオンライン相談 | サービス／相談用構成 | フォーム、入力検証、送信先、料金・説明・同意等を保持 |
| プライバシーポリシー | 法務／固定ページ用構成 | 法務文言・見出し・必要リンクを保持。記事カードを強制追加しない |
| お問い合わせ | 固定ページ／フォーム用構成 | 既存フォームの処理・動作を保持 |
| 管理画面・AI編集部・内部ツール | 今回の初期移行対象外 | 通常公開記事の枠を適用しない |

英語は原則として上記種別の言語差分で扱い、別系統の部品を無制限に増やさない。ただし既存の翻訳・構造・未翻訳ページの扱いは保存する。
新しい例外は、用途・既存ひな形で不足する点・専用領域・共有部品・影響範囲・検査方法を記録する。目的の異なるページを「標準と違う」という理由だけで欠落扱いしない。

## 4. 生成と編集の原則
- ひな形と固有内容は**公開前に**組み合わせ、閲覧者には完成した静的HTMLを配信する。
- ヘッダーや本文をブラウザの追加取得に依存させる方式へ、今回の移行だけを理由に変更しない。
- 本番とPreviewで同じ生成処理・依存関係を使用する。公開成果物には未展開の指示、下書き、秘密情報を含めない。
- ソースと生成済みHTMLの役割を明示する。移行後の生成物は直接手直しせず、正本側を直す。
- ただし移行前の現行 `articles/*.html` を生成物だと誤認して編集禁止にしない。
- 決定的な生成、欠落値・不明レイアウト・重複URL・再帰参照等の検出を実装要件とする。失敗時に古い／一部だけの成果物を公開しない。
- テンプレートエンジン・ディレクトリ・データ形式・移行対象一覧の形式は、パイロット設計で決定し、正本パスと編集例を文書化する。ローカル試作は採用済み方式ではない。

## 5. 保存する既存要件
- URL、本文、タイトル、meta、canonical、OGP、hreflang、画像・alt、アンカーと既存導線を保存する。
- 日英の対応先は実在するページを使用する。対応記事がない場合のトップ退避等は既存ルール・文言と整合させる。
- 検索プログラムの共有、記事評価の固有slug・一票制・配置、フォームの処理を保持し、二重読込しない。
- 支援リンクは既存の正式URLを維持する。収益導線、広告表記、商品リンクを変更しない。
- トップ棚4件、新着7件、人気記事の既存10件等は各現行正本とページ固有設計を守る。共通化を理由に件数を変えない。
- 人気記事JSONと同期処理、検索インデックス、sitemap、IndexNow、画像最適化、Preview隔離の依存関係を調べてから生成工程へ接続する。
- 特にテンプレート変更で生成HTMLが変わる場合、ソースの `.html` 差分だけを見ている通知・監査処理が取りこぼさない設計を記録する。生成日時だけで内容更新日を一括更新しない。

## 6. 既存ルールとの境界
- 完全コピー指定は、未移行ページの制作・既存構造の参照基準として残す。移行済みページ・登録した新規ページでは利用可能なひな形の選定へ読み替える。
- 初回移行は、方針採用と実装依頼の対象範囲を確認した別PR内に限り、台帳へ「移行中」と登録して部品抽出・生成検証を行える。これを移行完了や本番反映と扱わない。検証したcommit・正本・生成先・公開状態を記録し、他ページへ自動拡張しない。
- 新規記事はURL・種別・言語・使用ひな形の版・正本・生成先を台帳に登録する。同じ種別の1ページが移行済みでも、種別全体を移行済みと推定しない。
- 通常の記事制作で独自CSSを増やさない規則は維持する。承認された構造移行PRに限り、表示を保つ部品分離・共通CSS化を対象として明示できる。
- `articles/**` を原則触らない等の制限は通常の導線タスクで維持する。構造移行は対象URL・正本・出力差分を限定した別タスクで扱う。
- Step 1／Step 2を維持し、構造移行へ新記事公開・導線追加・本文改善を混ぜない。
- 完成・凍結状態と更新日ガードを確認する。承認済み移行対象に含まれる場合も、内容保存を証明し、凍結記事の本文を再改善しない。公式資料確認日・記事内容更新日を機械的に今日へ変えない。
- 内容を変えない構造保守に検索データによる本文再設計を混ぜない。実質的な内容変更が必要になれば別案件として既存の事前確認へ戻る。
- AI編集部の一時閉鎖状態や画像・検索データの運用経路を、今回のひな形移行で再開・交換しない。

## 7. 段階と承認
1. **ルール案**: 既存ルール横断確認、差分案、例外、引き継ぎ入口を文書PRにする。コード移行なし。
2. **方針採用**: 管理者の採用判断と対象文書版／commitを記録する。採用は本番一括移行許可ではない。
3. **パイロット**: 通常記事・トップ等の限定対象でソース／生成物の構成を決め、比較検査・Preview・戻し方を用意する。特殊ページを無理に含めない。
4. **段階移行**: ページ種別ごとに対象リストと例外を明示し、検査を通した単位で進める。
5. **本番反映**: 管理者が具体的な最終Previewと変更範囲を確認した後に実施する。

上記は作業段階の区別であり、各段階に一律の追加承認を設けるものではない。管理者が既に明示した採用・実装依頼は対象範囲と根拠を記録して引き継ぎ、通常の設計選択や検査ごとに再確認を求めない。現在の依頼が文書のみなら、その範囲で完了する。

このサイト全体の生成方式変更はHIGHとして扱う。既存の本番公開承認を省略しない。ルール案の検討中にサイト移行を再開しない。新しいチャットは移行状況を確認して現在段階から再開する。状態が変更された際は本書の提案表記・DecisionのStatusも同時に揃える。

## 8. 各実装PRの完了条件
- 対象全ページの生成成功、ソース→出力URL対応、未移行ページとの共存、対象外差分なし。
- 既存本文・リンク・画像・SEO値・記事固有データの比較。差分が出た項目は意図と根拠を記録する。
- PC・タブレット・スマホで構造の異なる代表ページを比較。全対象は静的監査、例外は個別確認する。
- 固定ヘッダーの重なり、幅、言語メニュー、検索、ヒーロー、カラム、フォーム、評価カード、支援、関連記事、フッターの該当機能を確認する。
- ひな形を一か所変更すると利用ページに反映され、対象外に波及しない検査を含める。
- Previewと本番のビルド一致、noindex・canonical・計測の分離、通知処理との整合を確認する。
- 変更前commit、生成手順、依存関係、ロールバック方法、検査結果、未確認事項、利用ページ一覧を残す。
- 文書だけで検査が実装済みとは扱わない。未実施を合格と書かない。

## 9. 再開時の手順
`AGENTS.md` → 上位原則／マスタールール → 本書 → 移行状況 → 作業別正本の順に確認する。対象ブランチ・未完了PR・現在段階・最後に通った検査・管理者判断を照合する。
共通部品を変更する場合は利用ページ一覧から影響範囲を出す。新規記事はページ種別と移行状態を確認して正本を選ぶ。ルール変更と実装完了を混同しない。
