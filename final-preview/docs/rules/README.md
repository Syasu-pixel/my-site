# ルール確認の入口と完了条件

対象は Syasu-pixel/my-site の全作業。通常のChatGPTチャット、Codex、新しい担当への引き継ぎで共通に使用する。管理者の今回の明示指示と既に受けた許可を引き継ぎ、同じ許可を繰り返し求めない。この確認手順は公開許可や停止中機能の再開許可を新たに与えない。

## 「ルールを確認して」と依頼されたとき

1. 対象リポジトリ・ブランチ・commit、現在の依頼、既存PR・未完了作業を確認する。手元の古いコピーだけで最新と断定しない。
2. **案件・連載・設備・機能ごとの固有正本を探索する。** `main` だけでなく、関連する未マージPR・Draft PR・作業ブランチも、案件名・記事slug・設備名・既知のファイル名で検索する。`docs/sample-lines/**`、`docs/plc-projects/**`、`docs/reference-notes/**` などは代表例であり、場所を固定して存在しないと判断しない。既存の `master-spec`、decision log、I/O表、仕様書、引き継ぎ文書等が見つかった場合は、新しい正本を作る前にその状態・更新履歴・適用範囲を確認する。
3. [正式一覧](index.md)を開く。機械処理の正本は [catalog.json](catalog.json)。開始時必須を本文まで読み、条件付き文書の存在と適用条件を**全件**確認する。短い依頼から作業範囲を確定できない場合は必須を読み、条件付きは適用性未判定として一覧に残す。無条件に対象外にしない。
4. 各文書を「適用」「対象外（理由）」「適用性未判定」に分類する。履歴・参考も関連する判断の根拠として必要なら読む。分類は重要度順や優先順位の代わりではない。
5. 適用文書を最後まで読み、その文書が要求する参照先を再帰的に辿る。循環参照は同一commit・同一パスを一度読んだ記録で解消する。参照先の適用条件も判断し、メーカー資料、記事別参照メモ、用語集、実装、設定、外部URL、画像等を必要に応じて確認する。ファイルの存在確認だけを内容確認にしない。
6. 下記の構造検査を実行する。実行不可なら未実行と記録し、取得できたGit tree等による手動照合と区別する。外部URLの到達性、見出しアンカー、動的なパス、内容上の矛盾は機械検査の保証外として別途確認する。
7. [既存不整合](conflicts.md)と新しく発見した矛盾を照合する。既存の明示された優先順位・限定例外で解決できるものはその根拠を記録する。未解決の重要な矛盾は該当する作業の判断を保留し、無関係な許可済み作業は進める。
8. 作業開始前と完了報告で、下記の確認状況を残す。追加・移動・参照変更や新しい依頼で適用範囲が広がった場合は更新する。

新規記事と既存記事更新の依頼では、[実作業手順](../article-editing-playbook.md)も適用する。

## 案件固有正本の探索・引き継ぎ

- `main` の検索結果だけで「案件資料は存在しない」と判断しない。関連するOpen/Draft PR、作業ブランチ、過去PRの変更ファイルを確認する。
- ユーザーが「前に作った」「元データがある」「構想を残した」「引き継いで」等と述べた案件では、過去チャットの記憶だけで新規設計せず、GitHub上の既存成果を探索する。
- 探索には、案件名、設備名、記事slug、シリーズ名、既知のディレクトリ名、`master-spec`、`decision-log`、`io`、`handoff` 等の具体語を使う。既知のPR番号やブランチがある場合は直接確認する。
- 案件固有正本が未マージPR/ブランチにある場合、その文書は「現行mainの採用済み共通ルール」とは区別するが、案件継続の一次資料として内容・状態・更新履歴を確認する。
- 複数の正本候補がある場合、作成日時だけで決めず、管理者の採用判断、decision log、更新履歴、実装・公開状態、後続PRとの関係を照合する。
- 既存正本があるのに、同じ目的の新しい `master-spec` やI/O正本を別場所へ新設しない。必要な場合は既存正本へ今回の決定を統合し、移動・改名・一本化は履歴と参照元を壊さない形で別途整理する。
- 未マージの案件資料をmainへ統合する際は、共通ルールと案件資料を混同しない。新規Markdownをmainへ追加する場合は、既存のルールカタログ登録規則にも従う。


## 確認状況の記録

依頼内容／対象commit／確認日時／一覧の版／構造検査の結果を先に記す。各文書と必要な参照先について次の列を記録する。条件付き全件の対象外理由は作業別にまとめてもよいが、対応するパスを省略しない。

| 文書・参照先 | 適用判断と理由 | 内容確認 | 参照先確認 | 矛盾・不足／次の対応 |
|---|---|---|---|---|
| 対象パスまたはURL | 適用／対象外／未判定 | 読了／一部のみ／未読／取得不可 | 完了／未確認あり／不要とした理由 | 根拠と残作業 |

記事制作・既存記事更新でPreview／公開まで扱う場合は、確認状況に次も残す。
- `docs/article-editing-playbook.md`、`docs/new-article-checklist.md`、`docs/cloudflare-preview-builder-finalization.md` の適用・読了状況。Heroを変更する場合は `docs/article-hero-templates.md` も含める。
- 最終承認用Previewが「編集元raw HTML」か「統合生成・公開候補」かを区別し、外部URLが実際にどちらを配信しているかを確認する。raw HTMLを最終承認用Previewとして扱わない。
- 最終承認用Previewの表示確認結果として、最低限 PCライト／PCダーク／スマホライト／スマホダークを記録する。専用レイアウトで必要ならタブレット幅も追加する。
- 最終確認専用PR・branch・Workflow・triggerを作った場合は、本番mainへ混入していないことと、公開後のクローズ／削除対象を記録する。

取得エラー、権限不足、読めなかった添付資料は「取得不可」。要約だけや途中までの表示は「一部のみ」。過去チャットで読んだという記憶だけでは最新版の読了にしない。

**「全ルール確認済み」は、対象commitを明示し、全件の適用性判定、適用文書の本文読了、要求された参照先確認、関連する矛盾の処置が完了した場合に限る。** 未読・一部のみ・取得不可・適用性未判定・必要参照の未確認が一つでもあれば使わない。「今回の適用範囲について確認済み」と対象と件数を限定して報告する。全件が読了でも内容理解・安全・実装の正しさを自動保証したとは言わない。

単なる「一覧を見た」「検索した」「構造検査が緑」は読了条件を満たさない。履歴・参考や対象外を未読のまま残すことは可能だが、その理由と範囲を明示する。

## 登録・参照を変更するとき

- すべての追跡対象Markdown/MDXを、フォルダを問わずcatalogへ登録する。非ルール文書も履歴・参考または用途に応じた条件付きとして登録し、未分類のまま消さない。
- 新規ルール・移動・改名・廃止は、同じPRでcatalogのパス・分類・条件、参照元、生成一覧を更新する。機能の停止だけでその禁止事項・再開条件を履歴扱いにしない。
- 非Markdownのルール・プロンプト・設定・検査もsupportingへ登録する。自動検出対象以外の独自形式は追加者が申告する。主要制御ファイルの自動検出は全コードの意味を判定するものではない。
- ローカル文書のリンクは文書からの相対リンクにする。コード表記は可能な限りリポジトリルートからの完全なパスにする。新しい未解決参照を黙って例外にしない。例示・歴史的記録・取得不可を残すなら参照元と元表記を個別登録し理由を書く。
- 別PRで追加された文書も、合流時に登録し直して検査する。固定した過去の全件数を完了証明に使わない。
- Preview・公開・Hero等の共通ルールを変更した場合は、該当する実作業入口とチェックリスト（少なくとも `docs/article-editing-playbook.md`、`docs/new-article-checklist.md`、必要なら `docs/article-hero-templates.md`）にも同じ判断条件を反映する。ルール本文だけ更新してチェック項目を古いまま残さない。

## 構造検査

リポジトリルートから `python scripts/check-rule-catalog.py --write-index` で一覧を生成し、`python scripts/check-rule-catalog.py --report rule-catalog-report.json` で検査する。`python scripts/test-rule-catalog.py` は登録漏れ・移動・リンク切れ等を検出できるかの回帰検査。

検査は全追跡Markdown/MDXの登録、分類・条件の記入、主要制御ファイルの登録、登録先の存在、Markdownローカルリンクとコード表記の具体的パス、古くなった例外、生成一覧の一致を確認する。レポートにはローカル参照、外部参照、動的パス、未解決参照の個別例外を残す。リンクの括弧を含む特殊記法・HTML埋込リンク・外部URL・アンカー・文章内の暗黙参照は網羅保証しない。確認担当が本文を読み補完する。

CIはPRごとに構造を検査する。required checkへの設定はこの文書追加だけでは変更されない。通常チャットがAGENTSを自動取得する保証もないため、[AGENTS](../../AGENTS.md)、[runbook](../agent-runbook.md)、[master](../ai-editorial-master-rules.md)を共通入口に接続する。
