# LINEスタンプ 制作ルール正本・一時保管

## この文書の扱い

- LINEスタンプ・絵文字の制作作業では、この文書を専用ルール正本として扱う。
- 画像生成、マスター作成、採用、一時保管、切り出し、main/tab作成、ZIP化の前に、**この文書を最初から最後まで全文読了する**。
- 過去チャットの記憶や「4×6」のような曖昧な表記だけで配置を判断しない。生成前後に本書の「確認用マスター配置の絶対条件」と「投稿用PNGの絶対条件」を確認する。
- 2026-10-04のアジ申請で、**直接透過PNG生成方式の方がグリーンバック方式より品質・量産性ともに安定する**ことを実地確認したため、以後これを標準方式とする。

## 標準制作フロー（直接透過PNG・独立24PNG正本方式）

1. 背景は**生成時点から透明（alpha付きRGBA PNG）**を標準とする。生成直後に実ファイルのRGBA／alpha有無を機械確認し、市松模様の見た目だけで透過と判断しない。
2. 12個×2枚や24個一覧で生成する場合も、それらは**制作ソース／構成確認用**として扱う。最終正本は必ず **01〜24の独立した24 PNG** とする。
3. 12個ソースは利用可能な**最大ネイティブ生成解像度**を使う。単純アップスケールを高解像度元絵の代用にしない。
4. ソースから01〜24を作る際は、各スタンプを**1個ずつ独立処理**し、魚体・文字・釣り竿・糸・ルアー・水しぶき・小物・装飾まで「そのスタンプ本人の要素だけ」で完結させる。
5. **一覧画像を均等分割しただけの24 PNGを最終成果物にしない。** セル境界を越える要素、隣コマとの接触・連結、隣コマ由来のゴミがある場合は、個別PNG化を完了するまで次工程へ進まない。
6. 01〜24をそれぞれ **370×320 px / RGBA / 透明背景**へ配置し、四辺に最低12px、可能なら14px以上の安全余白を確保する。一律縮尺ではなく、各スタンプの実要素に合わせて可能な範囲で大きく見えるよう個別調整する。
7. 24 PNG完成後に、その**独立24 PNGから**確認用 **横6列×縦4行** 一覧を作る。確認一覧から投稿用PNGを逆生成・再分割しない。
8. 確認一覧はユーザーが背景と透過を混同しない表示にする。チェッカーを使う場合は確認表示専用であり、PNG本体へ市松模様を焼き込まない。必要に応じて白等の単色背景版も提示する。
9. 投稿前に24枚全件で **他スタンプのゴミ0件／文字切れ0件／小物切れ0件／魚体切れ0件／空コマ0件／見切れ0件** を確認する。1件でもNGならZIP化しない。
10. 合格した独立24 PNGから main.png（240×240）と tab.png（96×74）を作り、**24＋main＋tab＝26 PNG** をZIP化する。
11. ユーザーがLINE Creators Marketへの登録・審査リクエストを完了した商品は、採用台帳を更新する。

## 24個一括生成について

- 24個一括生成は**禁止ではない**が、魚体・ヒレ・文字・小物の崩れが増える場合は採用しない。
- 24個一括でも品質が十分な場合は、そのまま採用してよい。
- 24個一括で細部が不安定な場合は、迷わず **12個×2枚** に戻す。
- 量産性を優先するため、6個×4枚を常用しない。12個×2枚で品質が安定しない場合のみ例外として6個単位を使う。

## 12個ソース生成時の配置・余白ルール

- 標準の **12個×2枚** で生成する場合も、各スタンプをそれぞれ独立したセル相当領域内に完結させる。
- 魚体・文字・釣り竿・糸・ルアー・水しぶき・小物・装飾を、隣のスタンプ領域へ侵入させない。
- 12個ソースの各コマ間には、後工程で安全に個別切り出しできる**十分な透明余白**を生成時点から確保する。
- 最終投稿PNGでは既存ルールどおり **最低12px以上、可能なら14px以上の安全余白**を四辺に確保する。12個ソース段階でも、この最終安全余白を確保しやすい構図・サイズで生成する。
- 12個ソースの時点でセル越境・文字の重なり・隣コマ要素の混入がある場合は、24個一覧への結合やZIP化へ進めず、問題コマまたはソースを修正する。
- 12個ソースからの切り出しでは、**固定等分だけで境界を決めない**。アルファチャンネルを走査し、文字・魚体・小物・装飾が存在しない**完全透明または最も透明度の低い「谷」**を優先して縦横の分割境界にする。
- 透明の谷が十分に確保できない境界、または境界付近に文字・キャラクター・装飾が接触している場合は、そのまま機械分割しない。問題コマ／ソースを修正してから再検査する。
- 透明の谷で切り出した後も、各コマを370×320へ個別配置し、最低12px、可能なら14px以上の安全余白を確保する。24枚一覧は完成した独立PNGから作成する。
- 分割時の近傍判定・連結成分・自動クラスタリング等で、越境した要素を後から別セルへ再割り当てして救済しない。
- 24個確認用マスターを画像生成で描き直さない。採用した12個ソース×2枚を機械的に切り出し・結合し、文字や魚体の再生成による劣化を防ぐ。

## 確認用マスター配置の絶対条件

- 最終確認用マスターは、**横6列 × 縦4行 ＝ 24個**で固定する。
- 「4×6」だけの曖昧な表記で判断せず、必ず **横6・縦4** と明記する。
- **横4列 × 縦6行は禁止**。
- セル境界線は描かない。
- 各セル相当領域には十分な余白を取り、文字・魚体・小物・装飾を隣セルへ侵入させない。
- 一覧マスターは確認用成果物であり、投稿用PNGそのものとは分けて扱う。

## 投稿用PNGの絶対条件

- 各スタンプは **PNG / RGBA / 透明背景**。
- 通常スタンプは **370×320 px** のキャンバスに収める。
- main.png は **240×240 px**、tab.png は **96×74 px** を使用する。
- 文字・魚体・小物・装飾を含む全要素をキャンバス内へ収め、**最低12px以上、可能なら14px以上の安全余白**を四辺に確保する。
- 端に近い釣り竿、糸、ルアー、水しぶき、文字の縁取りも「はみ出し判定」の対象とする。
- ZIP作成前に24枚すべてのアルファチャンネルを確認し、背景が本当に透明であることを検査する。
- 投稿前確認一覧はチェッカー背景で作り、透明部分と残留背景を目視できるようにする。
- **24 + main + tab = 26 PNG** のファイル数を機械的に確認してから提出する。


## 24分割・ZIP化のゴミ混入防止ルール

- 投稿用24分割では、**別セルの文字・魚体・小物・装飾を「近いセルだから」という理由で自動再割り当てしない**。
- 連結成分・近傍判定・自動クラスタリング等で隣セル要素を拾い直す方式は、**別スタンプのゴミ混入事故を起こすため標準禁止**とする。
- 各スタンプは、**生成時点から自身のセル相当領域内に完結**させる。文字・魚体・釣り竿・糸・ルアー・水しぶき・料理皿・装飾まで含めて、隣セルへ侵入させない。
- 24分割は、**横6列 × 縦4行の固定セル位置を基準**に行い、切り出し後に各コマを透明余白ごとLINE投稿サイズへ再配置する。
- 分割後は、必ず24枚一覧で次の3項目を全件確認する。
  1. **他スタンプのゴミ混入が0件**
  2. **文字切れ・小物切れ・魚体切れが0件**
  3. **空コマ・欠損コマが0件**
- 上記3項目のどれか1つでも問題があれば、**そのZIPを「最終版」「投稿用」として提出してはいけない**。
- 投稿用ZIPを提出する前に、確認用24枚一覧を作成し、ユーザーが目視確認できる状態にする。
- 安全余白は分割後だけでなく、**透過PNGマスター生成時点でも各セル内に確保**する。分割時に無理やり縮小して帳尻を合わせる運用は禁止する。

## グリーンバック方式の扱い

- **グリーンバック方式は標準方式から外す。**
- 旧資産の救済、または直接透過生成が失敗した場合のみ予備手段として使う。
- グリーンバックを使った場合、単純な「緑色を全部削除」は禁止する。シソ、ネギ、キャベツ、ルアー等の本来残す緑が欠けるため。
- 旧グリーンバック資産を透過する場合は、外周から連結した背景領域を優先して除去し、緑フリンジを別途検査する。
- グリーンバック由来ZIPを「正規の透過PNGマスター」と扱わない。

## 魚シリーズの24個ストーリー構成

- 魚シリーズは、各スタンプ単体でも会話に使えることを優先しつつ、24個を通して見ると「一回の釣行」が自然に流れる構成を基本とする。
- 基本の流れは、**「○○釣り行こうぜ！」などの誘い → 準備・出発 → 釣れた／よっしゃ／ちっさ／入れ食い／バレた等の釣行ネタ → その魚固有のあるある・シュール／狂気ネタ → 料理・食ネタ → また釣りに行こう → おつかれさま** とする。
- 日常会話だけの24個へ戻さない。魚種ごとの釣行シーン・釣り方・食べ方を主軸にする。
- 魚種ごとの特徴、釣り方、食べ方を優先し、魚を差し替えただけの同一24文言にはしない。
- シュール／狂気要素はグロテスクにせず、釣り人が思わず使いたくなるコミカルな狂気として入れる。
- 「釣りは狂気」などシリーズの強い個性は残しつつ、各魚種らしいネタを優先する。

## 魚体・作画の品質ルール

- 魚種ごとの解剖学的特徴を確認してから生成する。
- 胸ビレ、腹ビレ、背ビレ、尻ビレ、尾ビレの位置・枚数を混同しない。
- 同じ側に胸ビレが2枚以上見える、尾が2つある、顔が欠ける、余計な三角突起が増える等の**AI生成崩れは不採用**。
- ヒレを手のように使う表現をする場合も、本来の胸ビレを動かして表現し、追加の腕・ヒレを生やさない。
- 魚種固有の特徴を明示する。例：アジは**ゼイゴ（側線後方の硬い鱗）**を分かる範囲で表現する。
- リアル寄りの細かな表現は、直接透過PNG方式では積極的に使用してよい。ただし投稿サイズで潰れないことを最終確認する。

## 文字品質ルール

- 日本語文字は生成後に必ず目視確認する。
- 特に「釣」「刺身」「南蛮漬け」など画数の多い漢字は拡大確認する。
- 誤字、類似字、潰れ、意味不明な字形を見つけた場合はそのまま採用しない。
- 良い絵を全体再生成して壊さない。必要なら対象コマ・対象文字だけを修正する。
- 短く強い文言を優先し、LINE表示サイズでも読める文字量にする。

## LINE Creators Market タイトル・説明文の文字数ルール

- LINE Creators Marketへ登録する**日本語・英語のタイトルは、それぞれ40文字以内**で作成する。
- **日本語・英語のスタンプ説明文は、それぞれ160文字以内**で作成する。
- タイトル・説明文をユーザーへ提示する前に文字数を確認し、上限を超えた文面を提出しない。
- 英語版も日本語版と同様に文字数上限を厳守し、シリーズ名を付ける場合もタイトル40文字以内に収める。
- 文字数制限内でも、魚種名・釣りスタンプであること・シリーズの特徴が分かる簡潔な文面を優先する。

## ライブ対話時の画像確認

- ライブ対話でマスター画像を作成した場合は、生成完了だけで提示完了としない。
- **画像生成からチャット内へ直接表示する経路**を標準ルートとして使い、ユーザーが実際に目視できる状態にする。
- ユーザーが「見えている」ことを確認するまでは、採用・Google Drive一時保管・次工程へ進めない。
- 表示されない場合は、説明だけで代替せず画像を再提示する。
- 「裏で生成中」「最終確認中」と報告するだけで実ツールを実行していない状態を作らない。生成・加工は実際にツール実行してから進捗を報告する。

## Google Drive一時保管

- ユーザーが採用した画像マスター本体は、Google Drive の **「LINEスタンプ_採用マスター一時保管」** フォルダへ保存する。
- GitHubへ画像本体を一時保管しない。GitHubには制作ルールと採用台帳を残す。
- 正規マスターは原則として**直接透過PNG由来**とする。
- 12個×2枚で制作した場合、必要に応じて2枚のソースと24個確認用マスターの両方を保管してよい。
- ZIP作成時点では元マスターを削除しない。修正・再生成に戻れる状態を維持する。
- LINE Creators Marketへの登録完了をユーザーが確認した商品だけ、一時保管していた元マスターと一時ZIPを整理対象とする。
- **保管完了と報告する前に、Drive上に画像ファイルが実在することを確認する。台帳への記録だけでは保管完了としない。**
