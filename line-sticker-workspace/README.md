# LINEスタンプ 制作ルール正本・一時保管

## この文書の扱い

- LINEスタンプ・絵文字の制作作業では、この文書を専用ルール正本として扱う。
- 画像生成、マスター作成、採用、一時保管、切り出し、main/tab作成、ZIP化の前に、**この文書を最初から最後まで全文読了する**。
- 過去チャットの記憶や「4×6」のような曖昧な表記だけで配置を判断しない。生成前後に本書の「標準制作フロー」と「投稿用PNGの絶対条件」を確認する。
- 2026-10-04のアジ申請で、**直接透過PNG生成方式の方がグリーンバック方式より品質・量産性ともに安定する**ことを実地確認したため、以後これを標準方式とする。

## 標準制作フロー（2026-10-29改訂：1画像1スタンプ・10枚単位）

この節を今後の標準とする。従来の「12個×2枚」「24個一覧から分割」は**新作の標準として使用しない**。過去の作品で成功した方式は履歴として尊重するが、新作で勝手に旧方式へ戻さない。

1. 制作開始前にシリーズのキャラクター設定画・既存Vol.の24セリフ／構図を照合し、重複しない24種類を確定する。キャラの髪型、顔、衣装、小物と絵柄を固定する。
2. **1画像につき1スタンプだけ**生成する。10種類をまとめて進めるときも、**10枚の独立した画像**を出すこと。10コマを1枚に並べたマスター画像で代用しない。
3. 24枚は原則 **01〜10 → 11〜20 → 21〜24** の順に制作する。各回で個別画像を提示して採用確認を受ける。生成ツール側で同時に10画像を出せない場合は、個別生成を繰り返して10枚を揃える。架空の生成完了報告は禁止。
4. 生成の初期段階から透明背景（RGBA PNG／alpha付き）を指定し、**実ファイルのalphaを検査**する。市松模様・黒背景の見た目を透過証明にしない。画像全体の透明率だけでは背景残りなしと判定しない。
5. 個々の元画像から、**文字・髪・猫耳・手足・道具・効果線等を欠けさせず**、それぞれ **370×320px / RGBA PNG** に収める。初回から投稿用サイズを目標とし、生成解像度が異なる場合は採用画像を再描画せず縮小・配置する。
6. 四辺の安全余白は最低12px、可能なら14px以上。透明画素の外接範囲と目視で確認する。文字が読めるサイズを維持し、装飾の欠け・輪郭の背景残りも検査する。
7. **問題が出たスタンプだけを個別に修正／再生成**する。他の採用済み画像や、既に合格した番号は一切描き直さない。ユーザーの明示採用を無断で取り消さない。
8. 各10枚（最後は4枚）について、独立画像・番号対応・セリフ一致・キャラクター一致・透過・安全余白・見切れなし・他画像ゴミなしを確認して提示する。NGを「合格」や「投稿用完成」と呼ばない。
9. 24枚合格後に、**独立24 PNGからのみ**確認用 **横6列×縦4行** 一覧を機械的に作成する。これは表示・最終目視用であり、一覧画像から再切り出ししない。
10. 完成した独立24 PNGから main.png（240×240）と tab.png（96×74）を作り、**24＋main＋tab＝26 PNG** をZIP化する。枚数・サイズ・RGBA・余白を最終検査する。全件合格するまでZIPを正式完成品として出さない。
11. 日本語・英語のタイトル40文字以内／説明160文字以内を実際に数える。LINE Creators Marketへの審査リクエスト完了をユーザーが報告したら採用台帳へ記録する。

### 旧マスター方式の扱い（過去作品・例外のみ）

- 「12個×2枚」「24個一括生成」「6個×4枚」「一覧の分割」は過去制作の履歴・既存素材の修復時のみ参照する。**新作は1スタンプ1画像が標準**。
- 過去の一覧ソースを扱う必要が生じた場合、透明な隙間がない部分を固定等分・近傍クラスタリングで強引に切り分けない。別コマ由来の1pxの混入・文字欠けもNG。
- 旧一覧画像から生成した確認マスターを描き直して採用画像を失わない。ユーザーの明示許可なしに方式変更や採用画像の再生成をしない。
- 横6列×縦4行の配置は**24枚完成後の確認用一覧のみ**の規則であり、生成時に12枚や24枚を並べる指示ではない。

## 個別10枚生成：成功プロンプトの記録（2026-10-29 Vol.3）

### 実績と限界

- Vol.3の01〜10「今ひま？」「何時からやる？」「パーティー空いてる？」「VC入れる？」「聞こえてる？」「マイク切れてるよ」「準備できた？」「ロビーで待機中」「味方どこいった」「私に任せな」を、**独立した10画像として同じ生成依頼で出力できた**（2026-10-29、ユーザーの第一印象は「一発で成功」）。
- これは**生成と見た目についての成功例**であり、370×320px／RGBA／余白／ZIPの全数機械検査が完了したという意味ではない。出力モードや生成AIの挙動によって再現性は変わり得る。
- 失敗例：生成指示を「sticker sheet」「grid」「collage」「10種類を並べる」のように組み立て、**10コマの一覧画像**にしてしまった。キャラクター設定画の無視、余分な番号・説明文も発生した。

### 再利用するプロンプト構造（意味・構造の記録。実際の内部送信文の完全再現ではない）

次の形式で**個別画像を10件**生成する。生成システム側に複数画像の同時出力がある場合は10出力を指定し、ない場合は1件ずつ10回生成する。**1枚の画面内に10種類描かない。**

```text
Create ONE standalone LINE sticker image for exactly ONE phrase.
Character reference: [ユーザーが採用したキャラクター設定画像を参照]
Keep identical: [髪型・前髪・顔立ち・衣服・ヘッドセット・色・ちびキャラ比率]
Text in image: 「[この1件のセリフだけ]」
Pose and context: [このセリフで使う場面・表情・小物]
A single isolated character composition on real transparent background,
without any additional character, sticker, phrase, index, label or annotation.
No sheet, no grid, no collage, no contact sheet.
Include all lettering, accessories and effects inside safe margins.
Output an individual RGBA PNG. Final posting canvas: 370x320 px,
at least 12px transparent margin on every edge (prefer 14px).
```

- 10枚のバッチでは各番号の `Text in image` と `Pose and context` のみ差し替え、**別々の10枚**を出す。
- 生成画像が高解像度の場合は**採用絵柄を再生成せず**、縦横比を維持して透明370×320pxに収める。
- 文字化け・キャラずれ・非透過・余白不足を実ファイルで検査し、**NG番号だけ個別修正**する。10枚全部の再生成はしない。
- 成功した実画像の所在を保存する場合、GitHubに画像本体を置かず、既存のGoogle Drive採用マスターフローに従う。
- 10件をまとめて作ることと「画像内に10件描くこと」を混同しない。番号や制作上の注釈は**画像内に入れない**。

## 投稿用PNGの絶対条件

- 各スタンプは **PNG / RGBA / 透明背景**。
- 通常スタンプは **370×320 px** のキャンバスに収める。
- main.png は **240×240 px**、tab.png は **96×74 px** を使用する。
- 文字・魚体・小物・装飾を含む全要素をキャンバス内へ収め、**最低12px以上、可能なら14px以上の安全余白**を四辺に確保する。
- 端に近い釣り竿、糸、ルアー、水しぶき、文字の縁取りも「はみ出し判定」の対象とする。
- ZIP作成前に24枚すべてのアルファチャンネルを確認し、背景が本当に透明であることを検査する。
- 投稿前確認一覧はチェッカー背景で作り、透明部分と残留背景を目視できるようにする。
- **24 + main + tab = 26 PNG** のファイル数を機械的に確認してから提出する。


## 個別PNG・ZIP化のゴミ混入防止ルール

- 最終正本は01〜24の独立PNG。隣の画像から画素を拾ったり、一覧画像を等分割して完成品と呼んだりしない。
- 文字・キャラ・小物・効果線の欠け、誤字、透明部分への背景色混入、他画像由来ゴミ、空画像が1件でも見つかれば**その番号のみ**修正し再検査する。
- 24枚確認一覧は独立PNGから作成し、投稿前にユーザーが確認できる状態にする。
- 24 PNG＋main＋tabの26ファイル、各画像の寸法・RGBA・余白を機械的に検査し、目視確認と区別して報告する。

## グリーンバック方式の扱い

- **グリーンバック方式は標準方式から外す。**
- 旧資産の救済、または直接透過生成が失敗した場合のみ予備手段として使う。
- グリーンバックを使った場合、単純な「緑色を全部削除」は禁止する。シソ、ネギ、キャベツ、ルアー等の本来残す緑が欠けるため。
- 旧グリーンバック資産を透過する場合は、外周から連結した背景領域を優先して除去し、緑フリンジを別途検査する。
- グリーンバック由来ZIPを「正規の透過PNGマスター」と扱わない。

## 魚シリーズの24個ストーリー構成

- 魚シリーズは、各スタンプ単体でも会話に使えることを優先しつつ、24個を通して見ると「一回の釣行」が自然に流れる構成を基本とする。
- 基本の流れは、**「○○釣り行こうぜ！」などの誘い → 準備・出発 → 釣れた／よっしゃ／ちっさ／入れ食い／バレた等の釣行ネタ → その魚固有のあるある・シュール／狂気ネタ → 料理・食ネタ → また釣りに行こう → おつかれさま** とする。
- 日常会話だけの24個へ戻さない。魚種ごとの釣行シーン・釣り方・食べ方を主軸にする。
- 魚種ごとの特徴、釣り方、食べ方を優先し、魚を差し替えただけの同一24文言にはしない。
- シュール／狂気要素はグロテスクにせず、釣り人が思わず使いたくなるコミカルな狂気として入れる。
- 「釣りは狂気」などシリーズの強い個性は残しつつ、各魚種らしいネタを優先する。

## 魚体・作画の品質ルール

- 魚種ごとの解剖学的特徴を確認してから生成する。
- 胸ビレ、腹ビレ、背ビレ、尻ビレ、尾ビレの位置・枚数を混同しない。
- 同じ側に胸ビレが2枚以上見える、尾が2つある、顔が欠ける、余計な三角突起が増える等の**AI生成崩れは不採用**。
- ヒレを手のように使う表現をする場合も、本来の胸ビレを動かして表現し、追加の腕・ヒレを生やさない。
- 魚種固有の特徴を明示する。例：アジは**ゼイゴ（側線後方の硬い鱗）**を分かる範囲で表現する。
- リアル寄りの細かな表現は、直接透過PNG方式では積極的に使用してよい。ただし投稿サイズで潰れないことを最終確認する。

## 文字品質ルール

- 日本語文字は生成後に必ず目視確認する。
- 特に「釣」「刺身」「南蛮漬け」など画数の多い漢字は拡大確認する。
- 誤字、類似字、潰れ、意味不明な字形を見つけた場合はそのまま採用しない。
- 良い絵を全体再生成して壊さない。必要なら対象コマ・対象文字だけを修正する。
- 短く強い文言を優先し、LINE表示サイズでも読める文字量にする。

## LINE Creators Market タイトル・説明文の文字数ルール

- LINE Creators Marketへ登録する**日本語・英語のタイトルは、それぞれ40文字以内**で作成する。
- **日本語・英語のスタンプ説明文は、それぞれ160文字以内**で作成する。
- タイトル・説明文をユーザーへ提示する前に文字数を確認し、上限を超えた文面を提出しない。
- 英語版も日本語版と同様に文字数上限を厳守し、シリーズ名を付ける場合もタイトル40文字以内に収める。
- 文字数制限内でも、魚種名・釣りスタンプであること・シリーズの特徴が分かる簡潔な文面を優先する。

## ライブ対話時の画像確認

- ライブ対話でマスター画像を作成した場合は、生成完了だけで提示完了としない。
- **画像生成からチャット内へ直接表示する経路**を標準ルートとして使い、ユーザーが実際に目視できる状態にする。
- ユーザーが「見えている」ことを確認するまでは、採用・Google Drive一時保管・次工程へ進めない。
- 表示されない場合は、説明だけで代替せず画像を再提示する。
- 「裏で生成中」「最終確認中」と報告するだけで実ツールを実行していない状態を作らない。生成・加工は実際にツール実行してから進捗を報告する。

## Google Drive一時保管

- ユーザーが採用した画像マスター本体は、Google Drive の **「LINEスタンプ_採用マスター一時保管」** フォルダへ保存する。
- GitHubへ画像本体を一時保管しない。GitHubには制作ルールと採用台帳を残す。
- 正規マスターは原則として**直接透過PNG由来**とする。
- 標準の個別生成では01〜24の採用元画像を必要に応じて一時保管する。旧12個×2枚の作品では既存のソース保管履歴を尊重する。
- ZIP作成時点では元マスターを削除しない。修正・再生成に戻れる状態を維持する。
- LINE Creators Marketへの登録完了をユーザーが確認した商品だけ、一時保管していた元マスターと一時ZIPを整理対象とする。
- **保管完了と報告する前に、Drive上に画像ファイルが実在することを確認する。台帳への記録だけでは保管完了としない。**
