## 1. 目的と方向性
模型・プラモデル・ミニチュア・ジオラマ制作者のための「制作を記録する・集める・見せる・つながる」Webアプリ。趣味として長く使いたくなる、個人のアルバムとコミュニティを両立する。将来的には多言語展開、iOS/Androidアプリ、ユーザー間の作品売買仲介も検討する。

### 参考にする考え方
ヤマレコ、YAMAP、アングラーズなどの「個人記録＋一覧検索＋交流＋実績表示」の情報設計を参考にする。既存アプリの画面・文章・ブランド・独自表現はコピーしない。実在の競合や利用者ニーズは開発前に追加調査する。

## 2. 中心となるユーザー体験
1. 作品を登録し、制作工程を写真とメモで時系列記録する（未完成でも可能）。
2. 完成した作品が個人のアルバム／ショーケースに蓄積される。
3. 公開・非公開を選べる。公開作品は専用URLで共有できる。
4. ジャンル、キット名、塗料、技法等から作品や制作記録を探せる。
5. 他ユーザーの作品を参考にし、いいね・フォロー・バッジ等で交流する（段階導入）。
6. 将来、希望する制作者が作品を出品し、利用者間で取引できる機能を検討する（初期版には含めない）。

### 制作途中の公開と交流（2026-10-14 追加）
**合意した方向性**
- 作品の制作途中の記録は、完成を待たずに公開／非公開を制作者が選べるようにする。公開設定は後から変更できる設計とする。

**前向きに検討する機能（詳細未決）**
- 公開中の作品・制作工程へのコメントを通じて、助言・応援・意見交換をしながら作れるようにする。コメントの許可／停止、通知、通報・削除・ブロックを検討する。
- 複数ユーザーで一つの作品に関われる「共同制作モード」。共同編集とコメント参加は別権限とし、招待・編集範囲・履歴・作品の権利・離脱時の取り扱いを実装前に定める。
- 最初から共同編集機能まで作るかは未決。まずは公開制作記録＋コメントを基本にする案を比較する。

## 3. ページ設計案
- トップ: 新着作品、注目作品、ジャンル、サービス説明、投稿導線。
- 作品一覧／検索: キーワード、ジャンル、キット・メーカー、制作技法などの条件。
- 公開作品詳細: 写真、作品名、制作者、制作工程、塗料・工具、制作期間、公開日、関連作品。
- マイページ: 自分の作品アルバム、制作中・完成、下書き、公開設定、実績バッジ（後期）。
- 作品登録・編集: 写真、タイトル、ジャンル、素材／キット、工程、メモ、公開状態。
- 公開プロフィール: 投稿者が公開した作品・自己紹介を閲覧。非公開データは出さない。
- 後期: いいね・お気に入り・フォロー、週間／月間／ジャンル別ランキング、新人特集、コメント、通知、作品売買。

## 4. SEOと公開範囲
- **公開を選んだ作品**に固定IDと個別URLを発行（例: /works/{id}/{slug}）。URLの存在とアクセス許可は別概念。
- 公開作品は検索エンジンが読めるHTML（SSR/プリレンダ等）、固有title・description、適切なcanonical、画像altを提供する。公開URLをsitemapへ登録できる設計とする。
- 「公開」＝検索登録保証ではない。薄い・重複・不適切な投稿の自動インデックス促進は避ける。
- 非公開／下書きは認証・認可で保護し、sitemap・OGP・検索・公開APIから漏らさない。公開から非公開への変更や削除後のキャッシュ・検索反映も設計する。
- 投稿者の著作権・画像利用同意、第三者の権利、個人情報、公開範囲の説明が必要。
- 成長仮説: 公開作品が充実すると検索経由の発見・新規登録につながる。ただし指数関数的成長は保証されない。

## 5. 画像と保存方針
- 塗装・工作の細部を鑑賞できる品質を優先し、無理な画質低下を避ける。
- JPEG、WebP、HEIC等の受け入れ範囲を検討。RAWは原則として直接保存対象外とし、必要に応じ利用者に現像・変換を促す。
- 鑑賞用の高品質WebPを基本として保存し、一覧・サムネイル用の派生画像も必要に応じ生成。元画像はサーバーに保存しない（下記の投稿方針参照）。JPEG→WebP変換が画質改善になるわけではない。
- 画像のアップロード時検証（形式・実ファイル内容・容量・画素数）、EXIF位置情報の除去、マルウェア・権利侵害対策を検討する。
- 下書きは端末保存／同期も検討するが、共有投稿と複数端末利用にはサーバー保存が必要。
- 保存容量だけでなく読み書き処理・画像配信・データベース負荷・バックアップ・予算上限を設計する。

### 投稿画像のアップロード方針（2026-10-14 合意・構想仕様）
- 投稿数は原則として無料・有料とも無制限。料金プランの上限は「現在保存中の投稿画像の合計枚数」で管理し、画像を削除すると使用枚数が減る設計。無料100枚、月300円／1,000枚、月600円／5,000枚は検討用の例であり、料金・枚数は未確定。
- 利用者は端末上の通常の写真を選択するだけでよい。アップロード前に**ブラウザ内で自動的にWebPへ変換・必要に応じ縮小・圧縮**し、原本（JPEG／HEIC／PNG等）はサーバーに送信・保存しない。元画像は端末側に残し、利用者自身が保管する。
- 投稿の最終確認画面では**毎回、短い説明文**を表示し、ユーザーが確認してから送信する。文言案：「投稿画像はWebP形式に変換・圧縮されます。端末の元画像は変更されません。元画像はご自身で保管してください。」
- 変換後の画像を送信前にプレビュー可能にする。特に塗装・工作のディテールが損なわれないよう画質を比較検証し、画質設定や最大寸法は実機試験で決める。
- ブラウザ内変換に失敗したときは投稿を中止して理由と対処を示し、**原本を自動的に代替アップロードしない**。ブラウザ対応やHEIC等の読み込み失敗への対策を設計する。
- 運営側で扱うのは変換後の投稿画像と表示用派生画像のみ。ただし投稿用画像の保存、アクセス制御、削除、バックアップ・キャッシュ保持期限、配信費用、利用者による削除・退会処理は管理する。
- 投稿数無制限でもスパム防止のためレート制限・投稿サイズ上限等は別途設ける。画像形式・実体検査やメタデータの除去はサーバー側でも確認する。

## 6. 技術・運営の方向
- 本番のDenkicontrolとコード、DB、秘密情報、公開設定を完全分離。
- 新規専用GitHubリポジトリで管理。初期はWebアプリ／PWAを優先し、将来Capacitor等でiOS/Androidへ展開する選択肢を保持。
- 公開ホスティング候補: Cloudflare Pages等。画像保存候補: R2等。データベース／認証は要比較（Supabase等）。
- ログイン、作品、工程、画像、公開状態、ユーザー、反応を独立データとして設計。認可検査はすべてサーバー側で行う。
- 通報・ブロック・スパム対策・著作権侵害申告・削除依頼・運営モデレーションを初期から考慮。
- 収益化案は仮説: 大容量・便利機能の有料会員、将来のユーザー間取引手数料。売買は決済・本人確認・トラブル・権利者ルール・各国法令を確認後に判断。

## 7. 開発順序
**MVP**
1. 新規リポジトリ・環境分離・規約やプライバシー方針の準備
2. アカウント認証、作品の登録／編集／削除、制作工程、写真アルバム
3. 公開／非公開とアクセス制御、公開作品専用URL、作品一覧と検索、最低限の通報
4. モバイル操作性、画像品質と負荷試験、公開作品の検索エンジン向けHTML

**第二段階**
- いいね・お気に入り・フォロー、バッジ（作品数／制作記録など）、週間・月間・ジャンル別ランキング、新人発見、アルバムの見せ方。
- 人気順だけでなく、初心者・新着も発見される公平性、不正反応対策。

**第三段階（利用者・需要を確認してから）**
- PWA機能拡張、スマホストア配信、作品売買仲介、多言語化、収益機能。
